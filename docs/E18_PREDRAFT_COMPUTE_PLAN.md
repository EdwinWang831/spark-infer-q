# E18：真正减少草稿计算的可行性检查

在E17补训准备之后，先验证第二个空间：生成草稿前选择0/3/7个草稿，而非生成完整7个再截短。沿用同一Qwen、DFlash和Q4输出头；不下载、加载或训练主体权重。

现有BlockDraft支持4/8行，但训练检查点为8行。4行意味着实际4行backbone及3行Q4输出头，8行意味着8/7；四行模式可能改变前三个草稿，不能假设它等于七草稿的前三个，也不能直接套用七深度F1特征。0草稿仍需Target特征供后续轮使用，配对成本不等于完全禁用特征的纯Target服务。

先行单任务smoke通过后，固定12个E16 **train** 提示（英文/中文各6；解释、代码、长输入、数学、写作、实用指南），每提示serial greedy到EOS或40-token cap，在0/8/16/24位置对照。每位置实际生成3/7草稿，各宽度1..4/1..8及无草稿width1分别实测，三次计时，独立预热，检查serial输出、committed logits/live state。另验证Q4 M=3的存储权重算术；E6原检查只覆盖M=1/7/8。

成本必须区分初始cache构建和已有cache的追加。本probe模拟已有cache追加8行，冷启动成本单列，不能当成完整在线速度；测量顺序交错，报告不同block的接受进展和前三草稿差异。全部是训练前缀的反事实探针，不是新的holdout TPS。

若4行真实计算没有足够节省或接受损失抵消节省，则停在负结果；若出现可利用机会，再设计只使用本轮草稿之前可得信息的轻量gate（历史已提交信息、上轮置信度、上下文/剩余容量）。不能偷用本轮7草稿信号来假装提前跳过七草稿，也不能使用当前Target验证或未来EOS。最终需在新任务上完整在线比较，才能确认“另一部分空间”被打开。
