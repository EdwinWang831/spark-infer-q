# 提议：推理栈在日常使用中的轻量递归自我改进

状态：**PROPOSED v3，EV0–EV8 和 X1 均未执行，本方案没有新的 GPU 结果。** v1 写于 2026-10-23。v2（2026-11-02）根据之后的 E17–E58 结果做了四处修改：

- 重新评估每个可进化部件还剩多少收益空间；
- 把回放精度要求收紧到低于想检测的效应；
- 新增回顾式晋升审计、按请求选择执行配置、资源预算和进化账本；
- 把在线验证的基线换成原生运行时。

v3（2026-11-05）保留 v2 的证据、门槛和基线，改变方案的定位和主线：

- 目标是推理栈的轻量递归自我改进（RSI）。投机栈、DeepInfer 调度器和原生运行时是 RSI 的底座，也是第一批被改进的对象；
- 改进器自身的进化（递归层）从最后一个阶段提前为主线，先在模拟中做（EV5a），再上线复核（EV5b）；
- 新增冻结裁判原则：改进器可以改变自己怎么搜索，不能改变自己怎么被评判；
- 新增轻量性记账和可选的闭环实验（EV8）；
- 按 2026 年的 RSI 工作重写与已有工作的边界。

2026-11-06 补充（仍属 v3，没有新的实验结果）：

- 写明"回放逐层叠加"：GPU 采集、补全和校准一次，之后各层的进化都能在 CPU 上反复回放；列出它成立的前提和边界；
- 新增 EV2b 裁判强度曲线：输出保持逐位不变，只把评判速度的裁判有控制地变弱，测错误晋升如何变化；
- EV5a 新增第 5 组：改进器自己挑选留出数据；
- 新增白天 CPU 同址运行，以及 EV0 中的同址干扰门槛；
- 新增"第一层之外"和"研究议程"两节，不纳入最小闭环；
- 细化硬件形态：单用户台式机成为最理想情况的三个前提，以及两种常见例外；新增可选的第二平台阶段 X1。

下文引用的实验都是已完成的独立工程实验，不是 RSI 已运行或自动晋升的证据。实际排期时按阶段分配 E 编号；每个阶段执行前冻结输入、阈值和分析方法。所有提议的状态汇总在 [EXPERIMENTS.md](EXPERIMENTS.md#proposals-without-results-yet)。

## 要回答的问题

**主张：** 推理 infra 是做递归自我改进最合适的对象之一。在本仓库已验证的 greedy 逐位一致路径上，输出有逐位 oracle，速度可以配对实测，候选改动可以沿已有轨迹精确反事实回放。因此裁判客观、便宜，而且不受改进器影响。改进器可以在日常使用中只用空闲时间和单机资源，持续改进推理栈，也改进自己的搜索方式；整个过程不改变任何输出，不训练目标模型和草稿器的权重。候选只有在时间上留出的新数据中证明有收益才晋升。

草稿器、验证宽度控制器和草稿来源选择属于由目标验证兜底的 A 类表面；前缀状态缓存属于 B 类，必须另过逐位一致性门槛。在已验证的 greedy 数值路径下，输出轨迹与这些策略无关；补齐候选可能访问的每个位置的草稿和特征后，可以沿同一轨迹精确计算候选的 token 产出。耗时仍由成本模型预测，不能从输出一致性直接推出。这两点是 agent 外壳的自我改进不具备的：外壳的好坏只能靠重跑任务对比或大模型生成的测试来判断，没有真值。

**本计划中的"递归"和"轻量"（v3 新增）：**

- **递归：** 至少两层同时在改进，上层的改进由同一套冻结裁判在新数据上评估。L0 是推理栈部件（S1–S7）；L1 是改进器自身，包括触发规则、数据质量权重、各部件之间的预算分配、搜索空间和提出模板、回放补全的抽样率。见下一节。
- **轻量：** 不训练目标模型和草稿器权重，只重训 NumPy 线性预测头这类小模型；只在数据质量和漂移检测达标时触发；只用空闲时间，不提高 88 GiB 内存上限；每次晋升消耗的 GPU 时间、记录器开销和净节省时间都实测记账。
- **什么时候不称为 RSI：** 如果 L1 的进化在全新使用流上没有显著提高进化效率（EV5a），本计划只报告"安全的使用期进化"，不使用 RSI 的说法。

| 编号 | 问题 | 对应阶段 |
| --- | --- | --- |

## 递归结构与冻结裁判（v3 新增）

| 层 | 内容 | 谁能修改 | 怎么评估 |
| --- | --- | --- | --- |
| L0 推理栈部件 | S1–S7，见"L0 可进化表面与安全类别" | 改进器 | 精确回放、时间留出、序贯在线确认 |
| L1 改进器 | 触发阈值和数据质量权重；各部件之间的候选预算分配；参数搜索空间和编辑器提示模板；回放补全的抽样率；依赖复查的顺序。参数类直接搜索，规则类写成与 L0 相同接口的纯函数 | 改进器自己 | 元留出：在 L1 进化时从未使用的使用流上，从同一个 L0 起点比较新旧改进器的进化效率；同样遵守最小可检测效应和区间规则 |
| 冻结裁判 | 精确回放器、逐位 oracle、计时代码、成本校准协议、晋升统计规则（时间留出、最小可检测效应、序贯检验）、留出数据的随机抽取、账本审计器 | 只有人 | 由 EV0b 和 EV0 的结果选定，封存哈希后才开始进化 |
| 可信核心 | DeepInfer 调度器、MTPVarlen、E33 筛选头与回退路径、目标和草稿权重 | 只有人 | 见下文 E33 一节 |
| 权限与资源边界 | 可进化部件注册表和安全类别、GPU 时间上限、88 GiB 内存上限 | 只有人 | — |

四条原则：

1. **进化搜索方式，不进化裁判。** 改进器能改变自己找什么、在哪里找、什么时候找，不能改变候选怎么被判定；否则它可以靠放宽自己的门槛来"进步"。EV5a 的第 4 组专门测这种情况。
2. **改进器不能扩大自己的权限。** 它不能新增可进化部件、改变安全类别或提高资源上限，只能在给定预算内重新分配。
3. **每一层的晋升都可审计。** L1 的每次修改和 L0 一样写进进化账本，CPU 审计器能从封存记录重算。
4. **修改裁判是人做的独立实验。** 例如收紧门槛或更换成本模型；修改后从 EV0 起重新验证，不与进化收益混算。

这些原则来自本仓库自己的历史：E24 离线区间为正、E25 实测 −0.72%，E27 的在线费用修正实测 −0.53%。只看离线结果的改进器会晋升这两项（见 EV0b）。

## 回放逐层叠加（2026-11-06 补充）

**GPU 采集一次，CPU 回放多次。**

| 步骤 | 在哪里 | 次数 | 说明 |
| --- | --- | --- | --- |
| 正常使用，得到输出轨迹 | GPU | 本来就要跑 | 记下每个 token |
| 补全：在轨迹每个位置跑草稿器，记下草稿和特征 | GPU | 每个栈配置一次 | E20/E21：约为 decode 时间的 1–2.5 倍 |
| 成本校准：实测各宽度和配置的耗时 | GPU | 每个配置一次 | 在干净环境下做，见"白天 CPU 同址运行" |
| L0 回放：给定策略，逐轮算接受的 token 和预测耗时 | CPU | 任意多次 | 每个请求是几百次查表和加法 |
| 重训预测头、搜索参数 | CPU | 任意多次 | NumPy |
| 多天进化模拟（L1）、裁判强度曲线（EV2b） | CPU | 任意多次 | 把 L0 回放套进按天推进的循环 |

判断接受多少个 token 不需要重跑目标模型。greedy 下目标在每个位置的 token 已经在轨迹里；草稿与轨迹逐个比对，第一个不一致处由轨迹 token 纠正。这要求用宽度 w 验证时目标的输出与串行逐位相同，即 E8 起验证的行数无关 decode 算术。

**叠加。** 改进器（L1）每天决定是否触发、试哪些候选、晋升哪个。不管它怎么决定，使用者的请求流和模型输出都不变，变的只有耗时；而它当时会看到的每个评估结果，本身就是一次 L0 回放。所以任意 L1 策略下的整段进化过程，都能从同一份记录精确重放；更上一层同理。让进化安全的性质（不改变输出）与让进化可以低成本评估的性质（可以精确回放）是同一个性质。

拟写成命题：若每一层的可进化部件都属于 A 类或 B 类，则任意一层的进化过程，在 token 和决策上都能从一份完整记录离线精确复现，耗时由冻结的成本模型给出；证明对天数和层数归纳。配合序贯检验，可以进一步给出"晋升了实际变慢的候选"的概率上界。这部分须另行写出并检查。

**边界：**

- 只有 token 和决策精确，耗时是成本模型的预测。成本模型的系统性偏差可能偏向某类 L1 策略；因此 EV0 要求回放误差小于目标效应，EV4 增加 L1 回放保真度检查。
- 补全须覆盖所有 L1 策略可能用到的数据。若 L1 决定补全哪些位置，模拟时要先有全部位置的数据，再按 L1 的选择抽取；这是一次性的 GPU 成本。
- 大模型编辑器每次生成的候选不同，要么缓存当时的生成结果，要么模拟时重新生成（需要 GPU）。"只用 CPU"只对参数类 L1 严格成立。
- 回放默认请求流与系统快慢无关。系统变快后，使用者可能发更多、更长的请求；这只能在真实使用（U3）中观察，冻结的 U2 使用流观察不到。EV4 若使用 U3，须记录请求数和长度分布的变化。
- 随机采样、批量草稿（EV7）和 C 类改动下，回放不再精确。

## 统计设计：最小可检测效应（v2 新增）

- **实测分辨率。** E25、E27 各 108 次计时，E33 为 64 次配对计时，相对差的 95% 区间半宽约 0.5–0.9 个百分点。按 80% 把握度，一次在线对照能可靠检出的效应约 0.7–1.3 个百分点。[E12](E12_EXPERT_VERIFICATION_REPORT.md) 中单个动作的计时波动中位数为 3.5%，只能靠配对和重复压低。
- **回放误差必须小于目标效应。** v1 的 EV0 允许按任务中位相对误差 3%，比 S1/S3/S4 已测到的效应（0.1%–1%）还大，用它判断这些部件没有意义。v2 的门槛见 EV0。
- **晋升门槛随效应大小调整。** 回放预测收益低于 max(1.5 个百分点, 3 × 回放误差) 的候选不进入在线确认，攒在一起或放弃；超过的才做在线配对确认。
- **在线确认用序贯检验。** 停止规则预先冻结、可以随时停，既不为小效应跑过多计时，也避免反复看结果带来的假阳性。

## 预算与资源约束（v2 新增）

| 预算 | 依据 | 约束 |
| --- | --- | --- |
| 夜间 GPU 时间 | [E20](E20_FAST_COLLECTOR_REPORT.md)/[E21](E21_ADAPTIVE_COLLECTOR_REPORT.md)：补齐一个 192–384 输出 token 请求的全部位置标签，串行采集 9.6–20.2 秒；按 40–48 token/s 的 decode 速度估算，约为该请求 decode 时间的 1–2.5 倍。自适应采集器再省约 21% | 一天 2 小时的 decode，全部补齐要约 2–5 小时夜间 GPU。超出时按任务族分层抽样，抽样率写进账本 |
| 内存 | 常驻 worker 基线 allocated 约 72 GiB；两个 256K 请求峰值 81.14 GiB，分配上限 88 GiB（[E53](E53_LONG_CONCURRENCY_REPORT.md)、[E55](E55_RESIDENCY_REPORT.md)） | 进化任务与服务共用常驻进程和串行队列，只在没有活跃请求时运行；不提高上限，不重载模型 |
| 线上开销 | E22：纯 Python MLP 每次预测 0.3353 ms，NumPy 0.0118 ms，这类开销足以抵消 0.5% 级的决策收益 | 记录器和候选策略的 CPU 开销都计入计时；记录器自身的开销在启用前单独测出，须低于 0.2% |

**轻量性记账（v3 新增）。** 每个模拟或在线的"天"记录：夜间 GPU 时间（补全、训练、校准、在线确认分开记）、CPU 时间、峰值内存、记录器开销和编辑器生成的 token 数。报告净节省时间，即使用期节省的请求时间减去进化消耗中与服务争用的部分，以及回本所需的天数。夜间空闲 GPU 时间不与服务争用，但仍单独报告总量。EV2 的定时进化组和无防护组用同一套记账比较。

**白天 CPU 同址运行（2026-11-06 补充）。** 回放、重训、参数搜索和 L1 模拟只用 CPU，不必等夜间空闲，服务路径基本不用的 CPU 核心可以用起来。但 GB10 的 CPU 和 GPU 共用同一块 LPDDR5X 内存，不占 GPU 算力不等于不影响 GPU：

| 共用资源 | 可能的影响 | 依据 |
| --- | --- | --- |
| 内存带宽 | decode 受内存带宽限制，CPU 大量读写会抢 GPU 的带宽 | 每次前向读约 5.8 GB 共享权重 |
| 引擎自己的 CPU 线程 | 调度、kernel 启动和 Graph 发射被挤占，decode 变慢 | E22：0.3 ms 级的 CPU 开销就能抵消 0.5% 级的收益 |
| 功耗与温度 | CPU 满载可能压低 GPU 频率 | 记录器记录 GPU 频率 |
| 内存容量 | 回放数据与服务共用统一内存 | 服务分配上限 88 GiB |

后台负载不影响 token 数据，只影响计时数据。所以：

- 回放、重训、搜索和模拟白天可以运行，只使用已封存的成本曲线；
- 成本校准、在线确认和 EV0 的计时必须在后台暂停时进行；
- 后台任务限定在部分核心、低优先级，有请求时降速；记录器逐轮标记后台状态，计时数据按标记分开使用；
- 干扰成本计入轻量性记账。

是否允许白天运行，由 EV0 的同址干扰门槛决定。CPU 不是主要瓶颈：白天运行主要扩大搜索范围和 L1 模拟次数，晋升速度仍受新数据（时间留出）、GPU 补全和在线确认限制。

**与硬件形态的关系（假设，本仓库未测；2026-11-06 细化）。**

| 机器 | 同址干扰 | 精确回放 | 说明 |
| --- | --- | --- | --- |
| 单用户台式机，模型全部放进独立显卡的显存 | 预计最小：CPU 读内存条，GPU 读显存；CPU 核心多，推理时大多空闲；CPU 和显卡分别供电 | 容易：一次通常只跑一个请求 | 预计最理想，须满足下面三个前提 |
| 统一内存机器（GB10、Mac、Strix Halo 等） | 较难：CPU 与 GPU 共用内存带宽和功耗 | 容易 | 本仓库的情况，由 EV0 实测 |
| 台式机，模型部分卸载到 CPU（层或 MoE 专家放在内存里由 CPU 计算） | 可能比 GB10 更严重：推理本身就在用 CPU 和内存带宽 | 取决于引擎 | 跑放不进显存的大模型时很常见 |
| 数据中心多租户服务 | 小 | 难：batch 组成会影响数值（见 Re-feeding Is Not Replaying 和 EV7），需要 batch 无关的内核 | 不是本计划的目标 |

单用户台式机要成为最理想的情况，须同时满足三个前提：

1. 模型（目标、草稿器和本计划用到的表）全部放进显存。本仓库模型的目标权重约 70 GiB，另有 28.8 GB 的 n-gram 表，消费级显卡（通常 8–32 GB）放不下，所以那里要换更小的模型。
2. 推理引擎在验证宽度变化时逐位一致：用宽度 w 验证与串行逐 token 计算的结果完全相同。本仓库在 GB10 上由 E8 起的行数无关算术保证；常见本地引擎默认不保证。有些引擎提供批次无关的确定性模式，能否满足这一条须逐个确认。
3. greedy 解码。

跑小模型的本地用户多用独立显卡，属于表中第一行；跑大模型、尤其大 MoE 的，多是 CPU 卸载或统一内存机器，属于第二、三行。这是根据常见做法的判断，没有可靠的使用统计。X1 用第二个平台检验第一行。

## E33 补充：历史复现与当前冻结基线

本节依据主线提交 `2cb909b2abc902912033334d107e6cf56e795de9` 的 [E33 报告](E33_EXACT_HEAD_SCREEN_REPORT.md)、[线上对照方案](E33_ONLINE_PLAN.md)和[脱敏证据](../results/e33/2026-10-23-exact-head-screen.json)。E33 是人工设计、冻结后验证的优化；它提供当前执行路径和记录格式，尚未证明使用期进化有效。

- **已有结果：** 8 条已用 E28 工程 root、每组 4 次重复，共 64 次正式计时。原完整头 46.9088 → 筛选头 48.5063 token/s，+3.4055%，root bootstrap 95% 区间 +2.3853%～+4.1211%，四次重复均为正。两组各产出 8,588 个计时 token、验证 12,748 行，预算、接受和提交轨迹一致；token、提交 logits、DFlash 特征和最终 live state 检查通过。
- **机制与代价：** INT8 辅助头粗筛、定向 FP64 保守误差界、原 BF16 子集精算；不满足条件则回退原完整头。原 BF16 权重和算术保留，另加 640,665,600 bytes 辅助 payload。正常生成的辅助副本准备约 762.395 ms，Graph/JIT 等准备也在稳态 decode 计时外。完整头组件节时 36.24% 不等于 decode 收益；不得与其他实验的百分比相加。
- **适用边界：** greedy、单请求、容量 2048 的既有工程输入；自然回退 0/2,596 轮，候选并集 1～116。零自然回退不是新流量永不回退的保证。未验证随机采样、多请求 batch、4K+ 上下文或新的真实流量，未切换默认执行器/SSE，也不是独立官方模型数值等价证明。

| 基线标识 | 冻结配置 | 在本计划中的用途 |
| --- | --- | --- |
| H16 | E16 原有五种模式、模型、草稿器、成本与数值路径 | EV0 历史跨策略回放；EV1–EV2 历史数据方法验证，不代表当前最优基线 |
| B33 | E28 W8 草稿 MLP＋Q4 草稿头、E17 NumPy 线性预测、冻结 E29 W8 费用、E33 融合筛选头和私有 Graph | EV0 当前路径检查；EV2–EV3 当前栈回放的固定配置对照。精确沿用 E33 费用，先复现，再另立成本更新实验 |
| B33-full | 与 B33 相同，但使用 E33 的原完整 BF16 头 Graph | 数值、回退与成本诊断对照，不能单独作为 RSI 收益的主要基线 |
| R33（v2 新增） | 原生运行时的 [`--profile e33`](K3_E33_RUNTIME_USAGE.md)：与 B33 相同的模型、草稿、预测器、费用和筛选头，加上 [K4 开销修正](K4_RUNTIME_OVERHEAD.md)；同期 47.99 vs 研究路径 48.43 token/s，差 0.89% | EV4 在线验证和使用期部署的固定对照。使用期的请求走运行时，进化组与它同路径；不把运行时与研究路径之间 0.89% 的差距记作进化收益 |

执行前须为 B33 和 R33 冻结代码/二进制、target/draft 权重与量化 payload、预测器、费用、Graph 配置及数值范围/cap/回退规则的哈希清单；上述主线提交只是来源锚点，不能替代运行时输入 seal。B33 实际宽度选择沿用 [`choose_rows`](../spark_infer_q/confidence_head.py)，与 E33 实测一致；历史 H16 的 MTPVarlen 绑定另行固定，不能为统一接口而悄然替换。进化组和固定组共享相同执行路径，RSI 收益只相对于同一固定组计算，不能把 E33 相对完整头的 +3.4055% 记作进化收益。

**筛选头暂不列为可进化表面。** 它位于目标决策路径，不能归为"由目标验证兜底、只影响速度"的 A 类。其正确性依赖当前硬件、误差模型、数值范围、原 BF16 精算和回退契约；与可信核心一起冻结。将来若调整辅助格式、误差界、候选 cap、子集核或回退条件，须另立 B 类实验，先过数值契约、逐位 oracle 和完整生成门槛，再重新验证 EV0；EV0–EV4 不允许编辑器修改它。

E33 逐轮日志已有宽度、接受/提交、分阶段耗时、候选并集和回退字段，但只覆盖实际访问的位置。新宽度策略会改变步边界；须在 B33 自己的串行轨迹上补齐所需位置的草稿、特征和各宽度产出。E16/E17 的稀疏位置或 BF16 草稿标签不能直接充当 W8 草稿的完整反事实数据。筛选成本还受 hidden、宽度、候选并集和回退影响，原始 E29 费用不能被当作 E33 真实耗时；用独立校准数据建立 B33 的评估成本模型，并与供决策使用的冻结 E29 费用分开记录。改变步边界后，未记录的筛选行为须通过 GPU 补测，不能把同位置日志外推为精确计时。

| [TIDE](https://arxiv.org/html/2602.05145)、OSD、[EvoSpec](https://arxiv.org/abs/2605.27390)、[When Drafts Evolve](https://arxiv.org/abs/2603.12617) | 服务中在线更新草稿器；When Drafts Evolve 把草稿生成当作在线学习，用动态 regret 分析加速比 | 草稿器只是可进化部件之一；晋升需过时间留出检验，目标是不回退而不是低 regret；改进器本身也进化 |
| [Marconi](https://proceedings.mlsys.org/paper_files/paper/2025/hash/7c180af017258d239bac6248d1eb26ac-Abstract-Conference.html) | 混合模型前缀缓存的通用准入和淘汰 | 按使用者进化快照策略，并要求复用与重算逐位一致 |

投机解码由目标验证兜底，换任何草稿器都不改变输出，所以"无损"本身不是本计划相对第二张表的贡献。贡献在于不回退的晋升、精确的离线评估、覆盖草稿器以外的部件，以及递归层。

[Re-feeding Is Not Replaying](https://arxiv.org/pdf/2606.15621) 报告：普通推理引擎重放记录并不能复现当时的状态，只有在批次无关的内核下才精确。本计划依赖本仓库已经验证的逐位一致路径（E8 起的行数无关 decode 算术；联合 target 前向的输出也与分开执行一致），这是精确回放成立的前提，EV0 要先证明它。批量草稿不满足这个前提，见 EV7。

执行前须通读 Autopoiesis、Not-a-Bandit、Harness² 和 HarnessPro 全文，确认它们没有覆盖两张表的最后一列。Autopoiesis 和 HarnessPro 两行目前只依据摘要，Harness² 一行依据介绍文章。

| S7 | 多请求调度：prefill/decode 交错、联合预算、准入顺序 | A | 按批次组成校准的成本模型 | E48、K4 | EV7 |
| — | 目标模型量化、KV 压缩精度、近似验证、思考预算、采样参数 | C | 不纳入 | 压缩 KV 的精度门槛没过（E47、E55–E58） | — |

一个部件晋升后，依赖它的部件自动进入复查。例如 S3 改变草稿器精度后，S1 必须在新草稿上重新验证；S6 切换配置后，S4 的成本曲线要按新配置重新校准。S6 用到新的输入长度范围前，先补做该范围的逐位 oracle。

开启随机采样后，A 类的接受率估计必须遵守 MTPVarlen 的滞后约束，或另行证明不改变采样分布。本计划所有阶段只覆盖 greedy。

## 阶段与门槛

以下阈值都是初始建议，执行前冻结。不以单次计时噪声直接判定收益，沿用配对比较、按 root 分组的区间、逐重复敏感性检查，以及上文的最小可检测效应规则。

### EV0：回放保真度（地基）

- **历史复现 H16：** 用 E16 在线对照的逐轮日志（5 种模式，各 60 次计时，20 个任务）。在 Spark 上补算这 20 个任务串行轨迹每个位置的 DFlash 草稿，每个位置约 10 毫秒。然后只用某一种模式的日志，回放预测其余 4 种模式的逐轮决策、token 数和耗时，与实测比较。另外计算 E15/E16 离线评估所用的均匀前缀估计，与实测比较。
- **当前路径 B33：** 先用 E33 的 original/screened 日志复查相同步边界下的产出、数值检查与两种头路径的成本预测；两组原本决策一致，不能据此宣称跨宽度回放通过。随后冻结独立校准数据、补齐 B33 逐位置草稿/特征和宽度/筛选计时，并在预先冻结的宽度策略间补做配对实测，检验步边界改变后的回放。已有 E33 结果不替代这次验证。
- **自然实验检验集（v2 新增）：** 本仓库已有一批测出了方向和大小的配对在线对照：E17（六种模式）、E25（三种预测器）、E27（三组费用和运行时）、E29（Graph 与 W8）、E33（筛选头）。对每一组，只用其中一个模式的记录和补齐的逐位置数据，回放预测其余模式的差异，再与实测比较。前提是这些实验的逐轮原始记录仍在私有归档中；缺失的从检验集中去掉并写明。
- **指标：** 逐轮决策与 token 数的一致率；耗时预测误差；5 种历史模式的快慢排序是否保持；均匀前缀估计的误差；B33 跨宽度预测误差、候选并集和回退成本；自然实验检验集上预测差异与实测差异之差。
- **门槛：** 对每个被回放策略，逐轮决策、提交产出和拼接后的 token 序列与该策略实测完全一致。自然实验检验集上：
  - 实测区间不跨零的差异（E27 的实时费用修正、E29 的 Graph、E33），预测误差不超过 0.5 个百分点，且符号一致；
  - 实测区间跨零或对重复敏感的差异（E17、E25、E27 的 NumPy 运行时），预测值须落在实测区间内。
  - v1 的"按任务中位相对误差 3%、排序保持"保留为报告指标，不再单独作为门槛。

  H16、B33 和自然实验检验集分别报告，任何一项通过都不能替代其他项。
- **停止条件：** 达不到门槛且无法定位原因，就停止整个计划，因为核心主张不成立。
- **同址干扰（2026-11-06 补充）：** 在不同的后台 CPU 负载下（无、限定核心低优先级、满载），用 R33 测 decode token/s、TTFT 和重复计时的噪声。门槛：限定核心低优先级时，decode 减慢低于 0.2%，计时噪声不增大；否则改进工作只在无请求时或夜间运行。
- **资源：** H16 和自然实验检验集需 GPU 补算草稿；B33 还需 GPU 补测各宽度筛选/验证成本与配对 decode；同址干扰测试需少量 GPU 计时。回放与统计在 CPU 上完成，不改可信执行路径。

### EV0b：回顾式晋升审计（v2 新增，只用 CPU，可以最先做）

- **做法：** 把已封存的候选序列 E16 → E17 → E19 → E23 → E24 → E27 当作一段"进化历史"。用每个候选当时可得的离线结果，分别按四种晋升规则做决定：
  1. 离线点估计更好就晋升（无防护）；
  2. 离线区间下限大于零；
  3. 规则 2，且预测收益超过最小可检测效应；
  4. 规则 3，再加在线配对确认。

  然后用已测的在线结果判断每个决定是否正确。
- **已知部分：** 规则 1 和 2 都会晋升 E24 的 MLP（离线比线性 +0.21%，区间 +0.04%～+0.37%），而 E25 实测为 −0.72%（区间 −1.55%～+0.14%）。与 v1 设想的默认在线费用更新同类的 E27 实时修正，实测 −0.53%。规则 3 和 4 会拒绝这两项。
- **产出：** 一张"规则 × 候选 → 决定 / 实测后果"的表，作为 RQ3 的第一份证据，并给 EV2 的无防护对照组提供真实的失败模式。v3：人根据这张表和 EV0 的回放误差选定晋升规则，写进冻结裁判清单并封存；之后改进器的任何一层都不能修改它。
- **限制：** 只有约六个候选，这是案例研究，不是统计检验。

### EV1：数据充分性与漂移检测

- **做法：** 按 10%、25%、50%、100% 的训练提示组，分别重训 E16 的 F1 预测头，画出数据量和回放收益的曲线。按任务族排序，人为制造漂移，测校准漂移统计量的检出延迟和误报率。
- **依据（v2）：** E15→E16 加入新语言后 +3.18%；E17、E24 在同分布上追加数据约为 0。因此触发器以漂移为主，数据量为辅。
- **产出：** 冻结给 EV2 用的触发阈值：最少请求组数、各深度最少标签数、预计收益下限。
- **门槛：** 能定出一组阈值，使模拟漂移在合理延迟内被检出，且无漂移时误报率不超过 5%。
- **资源：** H16 数据分析只用 CPU；B33 曲线须使用 EV0 补齐、与当前 W8 草稿一致的特征和标签，再在 CPU 上拟合。

### EV2：模拟多天进化，单一部件

- **做法：** 在 U1 和 U2 上按天推进，只进化 S1（漂移触发）和 S4（配置变化后的重新校准）。先在 H16 历史数据上验证方法，再在通过 EV0 的 B33 完整数据上独立重复；不跨栈混用标签、费用或汇总收益。每一轮各设五个对照组：
  1. 固定配置（历史轮为 H16 的 E16 F1；当前栈轮为 B33）；
  2. 一次性调优，在第 k 天用同样多的数据调一次；
  3. 本方案，按证据分级触发，并遵守最小可检测效应规则；
  4. 无防护进化，只要最近窗口的点估计更好就替换，不做时间留出和最小效应检验；
  5. 定时进化，每天都重训。
- **指标：** 累计回放耗时；第二天速度；晋升次数；错误晋升次数，即晋升后在之后两天回放更慢的次数；相对于每天事后最优配置的差距；按"轻量性记账"计的进化消耗和回本天数。
- **门槛：** 本方案的累计耗时优于固定配置，区间下限大于零；不劣于定时进化，且更新次数更少。
- **如实报告：** 如果无防护进化并没有更多错误晋升，防护机制的价值就要降级表述。按 EV0b 的经验，同分布数据上本方案很可能多数时候选择不晋升；这本身也是结果。
- **资源：** 已完成各自数据补全和成本校准后，模拟与拟合只用 CPU。

### EV2b：裁判强度曲线（2026-11-06 补充，只用 CPU）

- **想法：** 输出保持逐位不变，只把评判速度的裁判有控制地变弱。每次晋升对不对，都用金标准判定：模拟中是精确回放下之后若干天的耗时，在线阶段再加配对确认。所以每个裁判的错误率都能测出来。
- **裁判：**

  | 编号 | 怎么判断候选更快 | 对应的常见做法 |
  | --- | --- | --- |
  | J1 | 精确回放 + 时间留出 + 最小可检测效应 + 序贯检验（本计划） | — |
  | J2 | 精确回放，不做时间留出 | 只看当下数据 |
  | J3 | 近似回放：E15/E16 离线评估所用的均匀前缀估计 | 近似模拟器 |
  | J4 | 一次在线计时的点估计，按 E12 的重复计时噪声模拟 | 重跑一次对比 |
  | J5 | 代理指标：平均接受长度，而不是耗时 | 常见的投机解码优化目标 |

- **做法：** 在与 EV2 相同的使用流和起点上，只更换晋升裁判，其余组件不变。先只进化 L0；EV5a 之后再让 L1 在各裁判下进化，看改进器是否学会利用裁判的弱点，例如在 J5 下提高接受长度但实际变慢。
- **指标：** 错误晋升率；被裁判判为收益、金标准判为回退的累计耗时；裁判预测收益与金标准收益之差随天数的变化。
- **门槛：** 这是测量，不设通过门槛；预先冻结要报告的曲线和区间方法。
- **如实报告：** 如果 J2–J5 的错误晋升并不比 J1 多，冻结裁判的价值要降级表述。
- **先例：** 强化学习中奖励模型过度优化的工作，用代理奖励模型对照金标准测出过度优化曲线（见"与已有工作的边界"）。执行前须查文献，确认自我改进系统上没有同类测量。
- **资源：** 只用 CPU，复用 EV2 的数据。

### EV3：扩展可进化部件

- **做法：** 按预计空间从大到小加入部件，启用依赖复查。
  1. **S6，按请求选择执行配置（最先）。** 用使用流中请求的输入长度分布，学习各配置的切换阈值，例如多长的输入启用 1024 行分块、专家 tile 和草稿上下文缓存。输出不变，所以只需按长度校准各配置的 prefill 和 decode 成本曲线。E42/E44/E13 的公开数据做初始曲线，用留出长度检验曲线；新长度范围先过逐位 oracle。
  2. **S2，整轮跳过草稿。** 先做只用草稿前已知信息的跳过 / 完整七草稿二选一门控（E18 的建议），在新任务上验证；记忆表和复制草稿器通过各自门槛后再并入。
  3. **S3，草稿精度。** 在夜间用 GPU 按候选精度重算草稿。
- **指标：** 每个部件单独以及组合后的回放收益；S6 同时报告 TTFT、完整请求时间和 decode 速度；依赖复查触发的次数和结果。
- **门槛：** 每个部件晋升的配置在时间留出数据上收益至少 2%，区间下限大于零，逐位 oracle 抽查通过。S6 的收益按使用流的长度分布加权；只在某一长度段有收益时，如实报告该段。
- **资源：** S6 主要是 CPU 回放加少量 GPU 校准；S2/S3 需要夜间 GPU。不改执行器的验证路径。

### EV4：在线验证

- **做法：** 冻结一段 U2 使用流，可选再加 U3，共 10 到 14 个压缩的"天"。每天的请求通过原生运行时、用当天已晋升的配置运行；两天之间运行一次进化任务。同一使用流上配对运行固定 R33 配置组，进化组也保留相同 E33 筛选/回退路径。在线确认按预先冻结的序贯检验进行。H16 只作历史诊断，不作为当前栈收益的主要基线。v3：改进器使用 EV5a 通过的 L1，未通过则用 EV1 的种子；L1 在 EV4 期间不更新。
- **指标：** 逐天的 decode token/s，以及 TTFT 和完整请求时间；全部正式输出与固定 R33 组和原完整 BF16 串行参考的一致性；提交 logits/特征/live state 的逐位 oracle 抽查；预计收益与实际收益之比；回滚次数；筛选候选数、回退率、辅助内存及准备成本。另报夜间补算/训练/搜索/验证用掉的 GPU 时间和记录器开销，不把稳态 decode 提升直接称为使用期总收益。
- **门槛：** 最后三天相对固定 R33 组的速度提升区间下限大于零；输出差异为零，数值 oracle 检查通过；预计与实际收益之比落在 0.7 到 1.3。对新使用流须保留 E33 的原完整头回退；若出现回退或候选分布变化，计入全部成本并复查预测校准，不把它单独视为输出错误。
- **L1 回放保真度（2026-11-06 补充）：** 在线阶段额外记录 L1 的每个决定。结束后用回放重放同一段使用流下的整段进化，比较回放预测的触发、晋升和逐天耗时与在线实测。预测误差须小于 EV5a 中 L1 各组之间的差异，否则 EV5a 的结论只作为模拟结果报告。
- **资源：** 需要原生运行时支持按请求切换配置版本，以及记录器；不改可信核心。

### EV5：进化器自身的进化（递归层，v3 改为主线）

v2 把这一阶段放在最后，依赖在线账本。v3 把它拆成两步：EV5a 在 EV3 之后用模拟账本先做，EV5b 在 EV4 之后上线复核。

#### EV5a：模拟中的元进化

- **前提：** EV0 通过，冻结裁判已封存；EV2、EV3 的模拟在 U2 的元训练流上产生了进化账本。
- **做法：** L1 只读元训练流的账本，调整触发阈值、数据质量权重、各部件之间的预算分配、搜索空间和补全抽样率；规则类候选写成纯函数。每个 L1 候选都在元训练流内部按时间留出评估。然后在元测试流上，从同一个 L0 起点各跑一遍，比较四组：
  1. 固定 L1：EV1 冻结的种子参数；
  2. 进化后的 L1，裁判冻结（本方案）；
  3. 无防护的 L1：在元训练流上点估计更好就采用，不做元留出；
  4. 可以修改裁判的 L1：额外允许它调整最小可检测效应和时间留出长度。这一组是消融，只在模拟中运行，用来检验原则 1。
  5. 改进器自己挑选留出数据的 L1（2026-11-06 补充）：允许 L1 决定哪些位置进入留出评估，而不是由冻结裁判随机抽取。这一组也是消融，用来检验改进器控制评判自己的数据时，是否出现自我确认的循环。
- **指标：** 无效触发率，即触发了但没有晋升的比例；每单位已确认收益消耗的 GPU 时间；获得首次收益所需的天数；预计收益的校准误差；错误晋升次数，即晋升后在之后两天回放更慢的次数；元测试流上的累计回放耗时。
- **门槛：** 第 2 组相对第 1 组，前四项指标中至少两项改善，按流分组的区间下限大于零，且错误晋升次数不增加。
- **如实报告：** 如果第 2 组不优于第 1 组，不使用 RSI 的说法。如果第 4 组的错误晋升并没有增加，"冻结裁判"的必要性要降级表述；第 5 组同理，对应"留出数据由裁判抽取"这条规则。元测试流少于 6 条时，作为案例研究报告。
- **资源：** 只用 CPU，复用 EV0–EV3 补齐的数据。

#### EV5b：在线复核

- **做法：** 用 EV4 的进化账本再更新一次 L1，在一段全新的使用流上比较原始改进器和更新后的改进器。
- **指标：** 与 EV5a 相同。
- **门槛：** 前四项中至少两项改善，区间下限大于零；否则保留原始改进器并报告。

### EV6：前缀状态快照（并行的工程线）

- **前提：** 执行器支持跨请求复用 GDN 和 QSA 状态，复用结果与从头重算逐位一致。快照必须与服务使用的状态格式相同；用压缩格式保存 BF16 服务的状态属于 C 类。
- **收益的变化（v2）：** v1 按 109 token/s 估计 2000 token 重算一次约 18 秒。之后 prefill 已大幅加快：[E41](E41_PREFILL_GRAPH_REPORT.md) 中 1,536-token 请求整体约 2.1 秒；[E46](E46_256K_REPORT.md) 的 256K prefill 为 1,137.5 token/s，262,080 token 约 230 秒。所以短上下文复用的收益已经很小，收益集中在几万 token 以上的 agent 长会话。
- **内存代价：** 4K 上下文的一个快照约 0.35 GB。256K 时一个 BF16 / FP8 / INT4 状态分别约 6.41 / 3.51 / 2.10 GiB（E55）。在 88 GiB 上限下，多存一个 256K 快照约等于少一个并发长请求，所以快照策略要和准入一起决定。
- **做法：** 在 U4 上比较四种策略：不缓存、最近最少使用、Marconi 式通用策略、按使用者进化的策略。
- **指标：** 首 token 延迟、token 命中率、快照占用内存，以及因快照占用而被推迟或拒绝的请求数。
- **门槛：** 复用全部通过逐位 oracle；进化策略的首 token 延迟优于 Marconi 式通用策略，区间下限大于零，且被推迟的请求不比通用策略多。

### EV7：多请求调度（v2 新增，等 K4 合入）

- **前提：** [PR #19](https://github.com/EdwinWang831/spark-infer-q/pull/19) 的双请求动态 DFlash 服务合入。草稿默认按请求顺序计算：批量草稿会让单个请求的草稿依赖同批的其他请求，逐请求精确回放不再成立。若要进化批量草稿，需另行证明可回放的方法。
- **做法：** 进化 S7，包括 prefill/decode 交错参数、联合预算开关和准入顺序。成本模型按批次组成校准（K4 已有按批次组成实测的成本表）。
- **指标：** 总吞吐、每请求 TTFT/TPOT 的 p95、最大输出间隔。E48 中交错调度已把一个 256K 请求的最大输出间隔从 225.42 秒降到 0.84 秒。
- **门槛：** 所有请求的输出与各自单独运行一致；吞吐和 p95 延迟都不劣于固定配置，且至少一项的区间下限大于零。

### EV8：闭环（v3 新增，可选）

- **想法：** 改进工作本身也跑在被改进的推理栈上。夜间补全（E20/E21 采集器）要用草稿器和目标做 prefill 与 decode；EV8 中编辑器是通过 R33 运行时运行的本机模型。L0 晋升后，这些工作应该随之变快，下一轮改进就更便宜。
- **前提：** 夜间补全和编辑器都走与服务相同的运行时和已晋升配置；否则这条回路不成立。如实写明哪些工作不受影响。
- **做法：** 在 EV4 的每个"天"之后，用固定的补全任务和固定的编辑请求各测一次耗时，比较当天配置与 R33 固定配置。
- **指标：** 补全每个位置的耗时；编辑器 token/s；每个夜间空闲小时内能评估的候选数；每次晋升所需的改进工作时间。
- **预期与边界：** 已测部件的收益都在个位数百分比（E16 新语言 +3.18%，E18 上界 +3.06%，S6 各长度段约 1%–7%），复利效应会很小。EV8 只证明回路闭合、测出闭合的大小，不声称改进能力在加速。
- **资源：** 每天少量 GPU 计时，与 EV4 共用记录器。

### X1：第二个平台（单用户台式机，可选，2026-11-06 补充）

- **目的：** 检验方法能换模型、能换硬件，并测量最常见的单用户台式机上的同址干扰。它同时回应"只有一个模型、一台设备"的质疑。
- **配置：** 一台带独立显卡的台式机，跑能全部放进显存的公开目标模型和公开草稿器，例如 8B 级目标模型配 EAGLE-3 一类草稿器；不使用 CPU 卸载。
- **前提：** 先证明该平台上验证宽度变化时逐位一致，与串行逐 token 对照 token 和 logits，做法同 E8。达不到就停止 X1，不用近似回放替代。
- **做法：**
  1. 在该平台上做一次补全和成本校准；
  2. 用同一套门槛跑 EV0 的回放保真度检查和同址干扰测试；
  3. 在 CPU 上复用 EV2、EV2b 和 EV5a 的流程，比较两个平台上的结论是否一致。
- **指标：** 回放保真度；同址干扰（decode 减慢、TTFT、计时噪声）与 GB10 的对比；EV2、EV2b、EV5a 的主要结论在两个平台上是否同向。
- **门槛：** 逐位一致的前提通过，回放误差满足 EV0 门槛。干扰和进化结论是测量，如实报告；结论不同向时，写明只在哪个平台成立。
- **资源：** 需要另一台机器。GPU 只用于逐位一致检查、补全、校准和干扰测试，其余在 CPU 上完成。

## 风险

- **回放保真度不够。** 若 EV0 失败，整个计划停止。
- **递归层没有收益。** L1 的搜索空间如果只有几个阈值，进化后的改进器可能与种子持平，也容易被看作给调参器调参。规则类 L1 候选（纯函数形式的触发评分和预算分配规则）与参数类一起报告；EV5a 不通过时不使用 RSI 的说法。
- **"有元层"本身不新。** Harness² 有持续的改进外壳，DGM 修改自己也提升修改能力，AlphaEvolve 改进过训练其底层模型的 kernel。本计划的新意要落在：裁判客观且冻结、候选可以精确离线评估、在使用期单机运行，以及 EV5a 第 4 组对修改裁判后果的实测。
- **v1 的主力部件收益已在分辨率以下。** E17、E24–E25、E27 表明，同分布重训和在线费用更新很难测出收益。如果 EV3 的 S6 和 S2 也没有超过分辨率的空间，本计划的主要贡献就是"安全的评估与晋升框架"本身，能挡住 E25、E27 这类回退；如实这样报告，不夸大为提速。
- **个人化没有学习曲线。** 若 EV2 的进化组与固定配置持平，说明在当前任务上个人化收益有限，如实报告；重心转向更依赖使用模式的 S6 和 S5。
- **每天的数据太少。** 一个人一天可能只有几万到几十万 token，触发会很少。可以把"天"合并成"周"，触发频率本身也是结果。
- **夜间预算不够。** 全部补齐标签约需 decode 时间的 1–2.5 倍 GPU 时间；不够时分层抽样，并报告抽样对回放误差的影响。
- **内存冲突。** 进化任务与长上下文服务争用 88 GiB 上限；只在空闲时运行，不为进化提高上限。
- **多请求下回放失效。** 批量草稿使逐请求的草稿依赖同批请求，EV7 之前不进化批量草稿。
- **计时噪声。** 沿用平衡顺序和夜间计时；计时不干净的时段降权或丢弃。
- **编辑器写出的策略代码有性能回退。** 逐位 oracle 拦不住变慢，所以时间留出检验、序贯在线确认和回滚不能省；策略的 CPU 开销计入成本。
- **领域变化快。** Autopoiesis、Harness² 和 HarnessPro 都是 2026 年的工作，后两者在 10 月发布；越早拿出 EV0b、EV0、EV2 和 EV5a 的结果越好。
- **同址干扰超过门槛。** 统一内存上的 CPU 回放可能抢走 decode 的带宽；超过门槛时改进工作退回夜间运行，主张中的"白天同址"相应删去。
- **第二个平台不满足逐位一致。** 常见本地引擎默认不保证验证宽度变化时逐位一致；X1 须先补齐这一点，可能需要改内核，工作量不确定。
- **新颖性待查。** EV2b 的裁判强度曲线、EV5a 第 5 组的自选评判数据，以及研究议程中的自筹预算，尚未专门查过文献；写进论文前须先查。

## 执行顺序

1. **EV0b**：只用 CPU 和已封存结果，可以马上做；先确认防护规则在本仓库历史上挡住了哪些回退。
2. **EV0**：先做 H16 历史复现和自然实验检验集，再完成 B33 当前路径的数据补全、成本校准和跨宽度实测门槛。E33 的既有 +3.4055% 不计入 RSI 增量。EV0b 和 EV0 完成后封存冻结裁判。同址干扰测试也在 EV0 中完成，它决定之后的 CPU 工作能否白天运行。
3. **EV1、EV2**：在各自数据与冻结栈内推进，模拟和拟合主要在 CPU 上完成。EV2b 紧随 EV2，只用 CPU。
4. **EV3**：先做 S6（主要是 CPU 回放加少量 GPU 校准），再做 S2、S3（需要夜间 GPU）。
5. **EV5a**：用 EV2、EV3 的模拟账本，只用 CPU。
6. **EV4**：需要原生运行时支持按请求切换配置版本和使用记录器；使用 EV5a 的结果。EV8 与它同时测。
7. **EV5b**：依赖 EV4 的进化账本。
8. **EV6**：独立的工程线，与 [Kaifra 路线图](KAIFRA_IMPLEMENTATION_ROADMAP.md) 的跨请求状态管理共用前提，可以和前面并行推进。
9. **EV7**：等 PR #19 合入。
10. **X1**：有第二台机器时，可以与 EV2 之后的阶段并行；优先做逐位一致检查和 EV0 部分。

**最小闭环（v3 新增，11-06 更新）：** EV0b、EV0（H16 和自然实验检验集）、EV1、EV2、EV2b、EV3 中的 S6，以及 EV5a（含第 4、5 组），就能回答 RQ2、RQ3、RQ6、RQ8、RQ11、RQ12，以及 RQ9 的模拟部分，构成"递归 + 冻结裁判"这个主张的最小证据。其中只有 EV0 和 S6 的成本校准需要 GPU。EV4、EV5b 和 EV8 把结论推到线上；EV6、EV7 扩展部件范围。X1 不在最小闭环内，但最能回应"只有一个平台"的质疑。

## 第一层之外（2026-11-06 补充）

本计划所有阶段都要求输出逐位不变，所以能改进的是"产出同样输出的代价"。代价不只是平均速度：

| 可以改进的 | 使用者的感受 | 已有例子 |
| --- | --- | --- |
| 平均 decode 速度 | 生成更快 | E33 |
| 首 token 延迟 | 更快开始回答 | E42、E44 |
| 最长输出间隔 | 不会突然卡住很久 | E48：225.42 秒降到 0.84 秒 |
| 内存与容量 | 放得下更长的上下文或更多并发 | E53、E55 |
| 稳定性 | 更少回退，不超内存上限 | E33 的回退计数 |
| 能耗 | 同样的工作更省电 | 未测 |

只做这一层是有意的选择，它换来了有逐位真值的裁判。以后要改变输出，有两条路，都不在本计划内：

1. **把省下的时间换成质量。** 推理栈仍然无损；另设一层决定省下的时间怎么花，例如在使用者可接受的等待时间内多思考，或多采样再验证。质量在有标准答案的任务上评判，例如数学答案和单元测试。
2. **按等级放宽裁判。**

   | 等级 | 判断标准 | 新增可进化的部件 | 裁判强度 |
   | --- | --- | --- | --- |
   | 1 逐位一致（本计划） | 输出每一位相同 | 宽度、草稿、执行配置、调度 | 最强 |
   | 2 分布一致 | 随机采样时输出分布不变 | 采样下的投机解码 | 强，需统计检验 |
   | 3 任务等价 | 输出可以不同，但任务测试照样通过 | KV 压缩、量化、近似验证（E55–E58 的压缩 KV 未过 3% logit 门槛） | 中 |
   | 4 质量裁判 | 大模型或人判断好坏 | 思考预算、提示策略 | 弱 |

在同一个系统上逐级下降，可以测出裁判强度与 RSI 安全性的关系。EV2b 先在第 1 级内部、只减弱速度裁判来做这件事。

## 研究议程（2026-11-06 补充，不在最小闭环内）

| 方向 | 想法 | 先要确认的 |
| --- | --- | --- |
| 递归 | **裁判的判决冻结，实现可以进化**：改进器可以加速回放器和采集器（E21 的自适应采集器已省约 21%），前提是在封存语料上判决逐位不变 | 判决等价检查的覆盖面 |
| 递归 | **主动选择补全哪些数据**：学习哪些位置的数据最能帮下一轮改进；留出数据仍由裁判抽取 | 与 EV5a 第 5 组的关系 |
| 递归 | **提出新的可进化部件，交给人批准**：把回路闭合程度变成可研究的变量 | 审批流程与权限记录 |
| 递归 | **递归深度受数据量限制**：每多一层，都需要该层从未见过的数据做留出；测一个使用者的数据能支撑几层 | 使用流数量 |
| 递归 | **用仓库的研究历史起步**：提出候选的大模型先检索本仓库的实验方案和报告（含被拒的候选），再提方案；改进器把自己的账本也加入检索库。测每个候选的晋升率和错误晋升 | 检索范围只限仓库公开文档，不读原始使用记录；生成结果须缓存以便回放 |
| 递归 | **改进器的世界模型**：成本模型随数据更新，但更新本身也要过冻结裁判（E27 的在线更新反而变慢） | 与 S4 的关系 |
| L0 个性化 | **PLE n-gram 表的常驻与预取**：按使用者常用 n-gram 的热度，调整 28.8 GB 主机映射表的页 | 统一内存上驻留位置对速度有没有影响 |
| L0 个性化 | **专家准备顺序**：按使用者话题的专家热度准备专家 | E52 的通用流水线未采用，需重新测 |
| L0 个性化 | **88 GiB 内存的分配**：KV、快照、Graph、草稿缓存之间按使用习惯分配 | 与准入一起决定 |
| L0 个性化 | **记忆表与复制草稿**：使用者反复出现的文本作为草稿 | 先过 S2 门槛 |
| RSI 安全 | **代理目标漂移**：递归越深，成本模型预测与实测的差距是否变大 | EV4 的预计与实际收益之比 |
| RSI 安全 | **适应性丧失**：改进器收敛到窄配置后，遇到新漂移是否适应变慢 | U2 漂移流 |
| 轻量 | **自筹预算**：当晚可用的 GPU 时间等于当天实测节省的时间乘以系数；研究 RSI 在经济约束下加速还是停滞 | 文献检查，例如 [The Economics of Recursive Self-Improvement](https://arxiv.org/abs/2609.15802) |
| 轻量 | **改进作业由可信核心调度**：改进作业作为低优先级请求进入 DeepInfer 调度器，与服务共用准入规则 | 调度器对低优先级请求的支持 |
