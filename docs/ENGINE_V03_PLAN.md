# 统一服务长请求 prefill 优化

2026-11-02。v0.2 已支持四运行槽、每请求32K，但四条32704-token输入的
完整请求约116秒，prefill仍逐请求推进。本阶段先减少同一工作量的实际成本。

候选：把已有E42/E44的1024行自主prefill和带SHA256校验的专家tile
接入统一服务；对照是当前512行、原专家路径。保留BF16 target KV、
动态DFlash、请求私有投影、四槽Graph、88GiB上限和8GiB主机余量。
不运行固定草稿对照，不提高准入超时，不修改另一工作区。

验收：

1. CPU：参数/静态检查边界、原双请求配置兼容、完整现有回归。
2. 同一常驻权重、同一套四槽Graph，对照/候选分别核对1024/1025/4096
   输入的末行完整logits、全部五层特征、有效状态及后续verify窗口。
3. 四条32704-token输入、每条64输出，同期ABBA两组配对。输出token、
   最终状态、特征、每请求预测率/验证宽度/接受轨迹必须一致。
   记录完整wall、TTFT、最大输出停顿、prefill/draft/verify/commit阶段成本。
   数值指纹在计时外获取，不把历史116秒当作同期对照。
4. 晋升要求完整cohort汇总wall至少减少5%，两组配对均更快；最后首token
   不退化超过2%；内存不突破原门槛。样本只支持该合成工作负载。
5. 最终公开服务另跑四请求HTTP及取消/恢复，验证实际启用新prefill路径，
   保留所有失败结果并更新中英文说明。

当前服务可通过现有SIGTERM处理退出到常驻作业循环，权重对象和PID保持；
测试和最终服务复用该session，不重载模型。长请求GPU合批与原生prefill
队列公平性仍是独立后续工作，不用本阶段prefill收益替代它们的证据。

## 用户补充：四请求 × 64K

用户在prefill实验进行中指定下一档为每请求64K、四个运行槽。上述32K
性能试验按原计划完成，结果不外推为64K性能证据。随后单独验收：

- 每条65472输入与64输出；四份BF16状态真实填满并同时驻留，仍在88GiB
  与8GiB主机余量内。更正mirrored feature ring的容量预算，计入两份镜像。
- 与原专家/512行prefill的同期64K baseline比较完整token、状态、特征与
  动态轨迹；四请求HTTP与隔离/target-only控制核对。计时后的指纹不计入wall。
- 在64K位置复核width1–8及部分提交、取消/幸存者、ID复用与容量拒绝。
- 最终服务采用通过门槛的prefill配置，默认准入提升至65536总tokens；
  保留原32K和双请求短配置，按实际预算拒绝超限组合。
