# E9：完整Q4动态decode时间分布

日期：2026-10-21（America/Los_Angeles）。[方法与修复记录](E9_PROFILE_PLAN.md)、[完整可审计数据](../results/e9/2026-10-21-decode-profile.json)。状态 **PASS_PROFILE_DIAGNOSTIC**。这是诊断，没有实施新的推理提速，也没有新的原生TensorFold排名。

**结论：target验证占主要时间，当前样本的GPU并没有大量等待Python供给。优先研究target GPU算子效率和验证预算的有效性；纯粹删除Python控制代码不能被预设为主要提速来源。GPU有内核在执行也不代表SM或带宽已充分利用。**

## 正常运行的粗分布

先对E8已有的40次完全未采样 rows8 动态请求重新汇总，不使用Python/Profiler插桩计时替代这组正常数据。共1,021个投机步、73.697秒decode；排除prompt、首个pending输出、加载、oracle和请求后状态检查。

| 阶段 | 总耗时 | decode占比 |
| --- | ---: | ---: |
| Target验证（含主机调用及同步） | 61.765 s | **83.81%** |
| 完整Q4草稿 | 10.608 s | **14.39%** |
| 接受前缀状态提交 | 0.983 s | 1.33% |
| 其他控制、CPU预测返回、context与流式输出 | 0.341 s | 0.46% |

这些是主机分段计时。target验证包含Python逐层调用、CUDA发射与等待，不能把83.81%直接解释为GPU计算。

## 有效GPU时间线

沿用同一target、rows8、完整词表Q4、BF16 backbone/selector/KV及E6成本/先验，选择中文JSON、thinking算术和capped256长代码。一次完整加载内，完成15次完整预热/验证（含12次独立完整生成logits/有效状态对照），再做15次请求（3次NVTX细分、12次NVTX未激活控制）。所有15次请求完整IDs和最终有效状态匹配，回归E7 IDs；72个采样投机步均选择宽度6，202,995个内核均关联到了发射调用，未发现丢失事件消息。

Nsight Systems 2026.3.1采用CUDA软件追踪，按三个NVTX decode根区间过滤，排除录制到的中间prompt、oracle和其他请求；这些记录不进入下表。GPU活动为kernel/拷贝/memset区间的并集，不是SM利用率。

| 场景 | 采样decode | GPU活动区间占比 | Kernel调用数 | 与真正未录制控制比较 |
| --- | ---: | ---: | ---: | --- |
| 中文JSON | 0.344 s | 81.39% | 11,284 | 采样/控制 1.172×（前两次控制） |
| thinking算术 | 1.103 s | 92.96% | 39,578 | 无同加载未录制控制，不能单独估计CUPTI总开销 |
| 长代码256-token前缀 | 4.076 s | 92.31% | 152,133 | 采样/控制 1.008×（后两次控制） |

三个decode区间共 **5.524秒**，GPU kernel区间并集 **5.064秒**，加拷贝/memset后活动并集 **5.068秒（91.76%）**。未记录到GPU活动的区间约8.24%，其中可能包含主机调度、驱动、PyTorch、采样器和其他开销，不能全部称为Python时间。三个样本及一次加载不代表新输入或长上下文泛化。

## GPU耗时大头

以下按全部内核的短名称家族汇总累计时长，不依据NVTX主机函数返回时刻判断GPU工作结束。内核累计时长与区间并集是不同口径；本轮它们接近，但一般情况下不得混用。

| Kernel家族 | GPU累计耗时 | 占全部GPU kernel累计时长 |
| --- | ---: | ---: |
| `nvfp4_expert_kernel` | 1.826 s | 36.05% |
| `qmmf_kernel` | 1.147 s | 22.64% |
| `_b16mm` | 1.007 s | 19.89% |

前三类合计约 **78.6%**。这是进一步检查专家核、量化投影和BF16矩阵乘的直接依据；当前没有硬件带宽/SM计数器，因此尚不能判定每个核究竟受带宽、算力或访存布局限制。

按内核发射所在NVTX区间归因，target 48层执行约占采样decode的70.74%，target finish（最终处理/输出头等）约8.35%，draft backbone约8.94%，draft head/top-k约2.64%，selector约0.09%，状态提交约0.80%。这些GPU区间可能跨过对应的主机函数返回时刻；不能把分组并集机械相加当作一般成立的分区。

例如draft head/top-k主机区间仅占0.71%，但它发射的GPU工作约占2.64%；selector主机区间占3.06%，其自身发射的GPU工作约0.09%，其余部分包含等待先前工作等。这证明按Python函数的主机耗时直接排列GPU优化优先级会误判。

## 同步与小控制环节

采样中主线程记录到867次同步调用，区间并集约2.689秒，占decode的48.69%；其中2.664秒与GPU活动重叠，即约99.1%的同步区间GPU仍在工作。target.run末尾显式同步的主机区间约占45.83%。这些时间主要等待先前GPU工作，不能当成删除同步后可直接省下的时间。

共202,995次launch调用，其主机区间并集约0.849秒，占decode的15.38%；其中0.773秒与GPU活动重叠。CPU API与GPU时间不是可相加的分区。Graph/原生发射仍值得单独A/B，但不能把15.38%或48.69%直接当作可兑现加速。

本轮主机标记中，context拼接约0.048%、预算选择约0.029%、反馈约0.034%、接受决策/预测CPU返回约0.127%、流式输出约0.253%。target特征捕获主机区间约0.711%，其发射的GPU工作约0.051%。这些是当前短上下文样本，不适合据此外推长上下文拼接成本，但不支持先大改小控制函数来追求主要收益。

## 可验证的下一步

1. **先查target重核。** 对`nvfp4_expert_kernel`、`qmmf_kernel`、BF16投影及target输出头做带宽/算力与布局诊断，再选择一个核或图执行边界作单变量A/B。每次保留输出、已提交logits和有效状态验证。
2. **研究验证预算的有效性。** E8这40次请求共验证5,492行，只提交3,348行；2,144行未提交，占39.04%。这不是39.04%的可直接省时比例：矩阵批量成本非线性，拒绝也不是事先已知。需要更好的预测，并以完整decode成本和已提交token衡量收益。
3. **草稿优先backbone。** Q4输出头已压缩，backbone仍是较大的草稿GPU成本。INT8 backbone＋BF16 selector可以另做质量/接受率/成本受控实验；不能把selector的主机等待误判为selector本身耗费大量GPU计算。
4. **Graph与同步清理保持独立对照。** 它们可以改善发射和流水，但当前样本GPU活动已较高；图执行若减少GPU调度成本或融合实际工作，潜力另行测量。仅消除全部空档、GPU工作量完全不变时，本次采样轨迹的理想上限约1.09×，不是所有算子/预算/量化优化的总上限，也不是无采样性能承诺。

## 采集故障和口径修正

- 默认CUDA硬件追踪预检未记录内核；切换`cuda-sw`后预检成功，未改内核权限或系统配置。
- 首轮`repeat:3:defer`发生Nsight agent EOF断连。请求输出和状态通过，但只恢复一份有效JSON时间线（GPU活动92.76%）；该样本与失败记录保留，**不加入主三样本汇总**。初始执行源固定在`d33c073`，已核对其源码hash。
- 重试使用一次连续录制、三个NVTX根区间，先让目标Python进程退出，再等采集器导出，取得完整三份区间。
- 连续录制期间，中间8个NVTX未激活控制仍被CUDA追踪，不能称为“未采样”。真正不在CUDA录制中的控制只有最前两次JSON与最后两次长代码，共4次；thinking的同加载控制无法单独估计CUPTI总开销。原runner contract仍保留原措辞，导出数据的`control_protocol_correction`和此报告按真实条件修正。主要正常阶段分布来自独立E8的40次完全未采样请求。
- JSON采样比前两次控制慢17.22%，长代码比后两次控制慢0.82%；运行成本反馈可能改变预算宽度，不能将差值全部归因于采样器。本轮采样72步均宽度6，完整逐次宽度分布保留。
- 当前perf权限不支持CPU栈采样，所以不声称精确识别了Python解释器、PyTorch C++与驱动各自的CPU成本。GPU活动覆盖也不代表满算力或满带宽。
