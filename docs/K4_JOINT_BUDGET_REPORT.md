# K4：实测批次成本与联合 E17 动态预算

**实现与正确性检查通过，服务性能晋升未通过。** 已保留 E17 接受率预测器，并接通基于实测批次成本的联合动态预算。直接调用有部分收益，但正式异步 SSE 三组均未超过同期原策略；独立带仪器复核又出现小幅收益，说明结果不稳定。默认继续使用原逐请求预算，新策略仅显式启用。当前并发上限仍为2，不将这一步称为4并发或完整K5完成。

[公开结果](../results/k4/2026-10-24-joint-budget.json)由 `k4batch_joint_export.py` 重算；[冻结成本表](../results/k4/2026-10-24-joint-costs.json)随代码保留，SHA256为 `494337bd1dcfa027041e65d3d2669687d8b01fb26d4e36f458143670f842390a`。本轮不与此前[轮询修复](K4_WAIT_FIX_REPORT.md)的不同测量轮次拼接计算收益。

## 决策发生在哪里

原流程在各请求完成草稿后，用当前 E17 累积接受概率和单请求E29成本独立选择q。新增 hook 在所有已调度请求的草稿/预测完成后、native ZOS metadata最终更新前，一起选择各请求q：

`score = 所有活动请求的预期输出token之和 / (一次批次验证成本 + 已支付草稿成本之和)`

每请求预期输出为 `1 + sum(当前E17概率的前q−1项)`。分子可由期望的可加性直接相加，不要求不同请求的接受事件独立。两个活动请求最多枚举64种合法宽度组合；q仍为动态1～8，受当前输出余量与native已预留行数限制。相同分数优先少做投机工作，并按物理slot稳定排序，返回时映射回native行顺序。

批次验证只收取一次联合成本，不把每请求单独费用相加；q按Target实际1/2/4/8补齐。已经生成草稿的请求即便最终选q=1也支付冻结草稿费用，最后只剩一个输出token时跳过草稿、费用为零。已取消请求不参与目标。保留E17权重、特征、NumPy float64实现、W8/Q4草稿、E33精确筛选、自然EOS、事件等待和原回收fence，没有新固定草稿模式。

`JointBudget`是当前已调度decode批次的预算选择器，不负责准入、公平性、抢占或全局调度。未启用时沿用原预算与执行路径；启用时通过artifact SHA、E17/W8/成本指纹、Target源码及Graph模式检查，拒绝不匹配的运行配置。HTTP服务新增成本文件/SHA两个成对参数，只有显式提供才启用。

## 先冻结成本，再评估

作业280在同一resident串行执行，使用独立的租约/重试合成上下文，构造64和1024 token两个上下文锚点，以768为短/长分界。采集两个物理slot的singleton及四种双请求上下文组合、全部物理bucket，合计80种配置×3次正式样本。各配置先预热头部子集JIT，再以三个固定随机顺序测量，取每格中位数。

成本从host launch计到verify/head/commit事件完成及ticket退休，包括必要主机推进；状态恢复、prefill、草稿和预热排除。每个窗口保留一个token后恢复seed，不用评估请求的未来接受情况拟合费用。已支付草稿成本沿用冻结W8短/长值约9.64/10.17ms，并在候选宽度中一致收费。

这是**物理bucket的近似成本模型**，没有声称精确覆盖所有候选集合、上下文长度、GDN parity或不同keep长度的费用。它不是GPU kernel纯计算计时，也没有把实时wall噪声喂回预算来追逐偶然较快的样本。

## 三种对照及正确性

作业281比较：

- `original`：当前E29成本下每请求独立选择，作为默认基线。
- `measured_singleton`：相同新成本表，但每请求各自按singleton费用选择，隔离更新成本表的作用。
- `joint`：相同新成本表，按整个活动批次的预期输出/费用联合选择。

三组固定负载，每模式三次直接调用正式计时，模式次序轮换，共27次。先做9组独立正确性检查，再排除诊断full head并预热正式路径；每次拒绝新JIT形状。计时从两请求都恰好输出一个token后到最终native退休，包括第一轮草稿，排除prefill。

改变预算会改变轮次与接受轨迹，不能再要求逐轮q/accepted列表与基线完全一致。本轮要求最终greedy token序列一致；每一步以独立eager缓冲即时commit核对logits、接受特征和有效状态，并在相同请求位置出现时核对E17概率相等。通过 **2619行logits、2136行特征、490次有效状态、1457次共享位置概率** 检查；80个Graph无fallback。

单位均为合计decode token/s；两条流合计，不是每条各自速率。

| 短英中，32/32输出 | 43.18 | 42.48 | 44.75 | +3.64% |

## 服务复核与归因边界

针对正式SSE回退，作业285另做三种预算×三组×四次的36次带仪器SSE运行。记录provider、预算hook、poll与事件等待的wall及CPU入口/出口；全部仍核对输出、无计时内JIT。它是另一次带仪器诊断，**不并入正式结果，也不据此覆盖之前的回退**。

| 负载 | 原预算 probe | 新成本独立 probe | 联合 probe |
| --- | ---: | ---: | ---: |
| 短英中 | 41.24 | 44.82 | 44.18 |
| 长短 | 57.55 | 61.02 | 58.17 |
| cap128混合 | 38.16 | 39.11 | 39.03 |

联合预算hook的中位wall约0.074ms、最大0.442ms；原hook约0.008ms。它有额外CPU开销，但这些数据不足以将正式服务数百毫秒的个别波动全部归因于预算枚举。草稿调用中位仍约11.5～11.7ms，个别可超过50ms，三个模式都观察到调用入口/出口CPU不同。API时间包含嵌套和prefill，不能相加或冒充纯kernel归因；仅有入口/出口CPU采样也不能证明某个操作系统机制。

复核方向与正式轮次不一致，因此当前没有稳定的服务净收益证据，也没有证明E17概率模型因为多并发而失效。联合预算仍使用同一个E17，改变的是费用与动作选择。

预算带来的工作量变化也有限：短组Target物理行106→103，forward仍18次；cap128组物理行322→301，但forward只从65→64、草稿次数75→74。新预算减少了一些padding，仍没有改变DFlash逐请求串行、混合请求长尾和不足的持续重叠。不能期待这一步单独让总吞吐成倍增长。

## 生命周期、资源和结论

本地236项测试，224通过、12环境跳过；新增共享费用目标、同bucket动作、输出cap、已支付草稿收费、物理slot映射、取消、缺失成本及配置指纹检查。作业283在联合预算启用时通过14项真实GPU NEXTN=0/7生命周期案例，覆盖EOS/cap、pending position、三种取消阶段、在途取消/survivor、同ID复用、有界关闭、native owner guard、故障隔离及新owner恢复。

GPU作业均通过同一resident队列串行处理，PID319、load_count=1。最终本轮286审计：没有活跃K4对象，Gloo/NEXTN环境恢复，二次GC后allocated稳定为77,762,506,752 bytes；相对此前事件修复后新增32MiB，与生命周期测试创建stream的库工作区块相符。未清空共享缓存、未重载模型。稍后worker状态采样已经执行到另一个研究作业，allocated发生变化；因此只将286作为本轮资源测量，不把后续全进程显存变化归因给本轮。

默认保留原逐请求动态预算。联合预算作为可复现研究选项，不晋升为服务默认，也不增加预测器容量。提高并发接下来仍需真正扩展请求槽位、控制Graph组合，并处理草稿合批；这轮交付的是可供后续使用和复测的批次成本/预算基础，尚未接入4请求执行。
