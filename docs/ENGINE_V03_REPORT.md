# Kaifra v0.3：prefill 提速与四请求64K

2026-11-02。[事前方案及用户64K补充](ENGINE_V03_PLAN.md) ·
[用法](ENGINE_V03_USAGE.md) · [English usage](ENGINE_V03_USAGE.en.md) ·

四请求32K配对试验中，较快的prefill配置使完整cohort耗时减少 **17.33%**。
四请求每条64K的容量、数值及HTTP验收也通过了。两个工作负载分别记录计时。

## 改动

统一服务增加 `--prefill-experts` 与 `--prefill-chunk-rows`，接入已验证的
E42/E44路径。候选同时采用1024行自主prefill、配套1024行原生prompt预算
和固定SHA256的专家tile；对照是512行与原专家路径。它是一组部署配置，
本轮没有逐项消融，不把收益全部归给某一个内核。

服务默认容量增至65536总tokens、保留四个运行槽。长路径仍是私有Graph
共用串行GPU工作区，KV保持BF16。启动首槽测量余量按64K调整，预算更正为
计入FeatureWindow的完整镜像存储：原32K准入公式少计了一半特征环，
四请求约少计0.195 GiB；旧实测峰值仍在限额内，历史预测不作改写。

## 同期32K性能

同一常驻模型和四槽Graph，四条32704输入、每条64输出，按ABBA运行。
数值指纹放在计时后；首token、排队、prefill、草稿、验证、提交及原生/事件
开销均在完整wall内。两种配置的token、最终状态、特征和每请求动态轨迹一致。

| 指标 | 原512行配置 | 1024行专家tile配置 |
| --- | ---: | ---: |
| 两次完整cohort wall | 114.474 /115.336秒 | 94.963 /95.012秒 |
| 平均完整cohort | 114.905秒 | 94.987秒 |
| 平均prefill累计时间 | 106.602秒 | 86.796秒 |
| 平均草稿累计时间 | 约1.710秒 | 约1.714秒 |
| 平均验证累计时间 | 约6.06秒 | 约6.06秒 |
| 最后首token时间 | 112.280 /113.153秒 | 92.771 /92.798秒 |

两组配对均更快，汇总耗时减少17.33%，通过事先至少5%及最后TTFT不退化
超过2%的门槛。对照中prefill占完整wall约92.8%；收益主要落在该阶段，
没有新decode提速结论。这里只有两组配对和合成重复提示，不是广泛流量统计。

较大prompt块使前几个请求的最长相邻输出间隔从约0.49–0.51秒变为
0.76–0.78秒。第一请求完成时间从38.55–38.80秒变为
40.76–40.87秒。其他请求的首token和总cohort更早，但不能称为所有延迟
指标都改善。兼容512行配置继续开放，原生prefill队列优先推进前序请求的
问题还在，未把本轮收益称作公平调度或长请求GPU合批。

## 四请求64K正确性

先用原专家、512行算术分别真实填充四条65472-token前缀，四份缓存同时
驻留。逐token生成64输出作为控制；保留前缀快照后，以真实DFlash provider
及SpeculativeBackend分别运行隔离动态控制。最终公开HTTP路径采用1024行
候选，混合SSE/非流式四请求；四条结果的token、完整已提交状态、特征与
动态宽度/接受/预测率轨迹全部一致。

隔离动态控制复用已填满前缀，执行实际草稿与verify/commit适配器；它不经过
原生Scheduler。HTTP路径另由真实原生Scheduler驱动，因此本轮没有把这组
控制描述为四次独立原生64K服务启动。

最终服务的独立客户端完整cohort耗时186.53秒，共处理261888输入与256输出
tokens。该计时包含prefill、调度和decode。排队、取消、幸存者重放与断连
检查结束后，19个请求正常完成，2个请求取消，worker失败为0。

在65472位置覆盖width1–8、两种GDN奇偶及部分提交，共16组完整logits、
特征和有效状态差分。利用append-only前缀不变量在同一私有状态上还原快照
比较Graph/eager，避免额外分配第五份64K KV；每次诊断后核对原前缀指纹。
超容量拒绝、取消64K请求、旧句柄拒绝与同ID复用通过。最终常驻服务另由
独立客户端验证四请求、四运行加四等待、第九请求429、取消幸存者与断连恢复。

包含控制快照与备用512行工作区的验证峰值为allocated **82.92 GiB**、
reserved **83.49 GiB**，最低主机MemAvailable为 **22.40 GiB**。
经更正特征环公式后的启动预测为83.52 GiB。88 GiB分配上限和8 GiB主机
余量保持不变；预测与实际峰值分别记录。

模型PID与权重对象贯穿32K试验、64K验收和最终服务，`load_count=1`。
使用原服务的退出处理回到常驻作业循环，没有重载模型、清理allocator缓存
或开启第二个GPU模型进程。最终服务启用64K及1024行专家tile；不提供扩展
路径的普通CLI仍保留512行兼容配置。

本地CPU检查共495项，454通过、41可选环境跳过。wheel及仓库外CLI检查、源码与
实际服务快照一致性见脱敏证据。长请求GPU合批、八请求、1M、预测器成本
重校准、跨模型泛化和长期压力仍未验收。
