# Kaifra 四请求 128K 验证方案

2026-11-03。用户要求在四请求 64K 的基础上继续扩大至每请求 128K。
总容量为每条 131072 tokens，包括输入与输出。四条正式请求各使用
131008 输入与 64 输出，保留动态 DFlash、BF16 target KV、现有专家 tile
及单一常驻模型。分配上限保持 88 GiB，主机可用内存至少保留 8 GiB。

首轮实测完整索引的四槽预测约 90.13 GiB，索引环为 88.65 GiB。
将草稿原参数改为既有融合矩阵的精确视图后，实际减少约 0.518 GiB
重复 BF16 存储。四请求 128K 默认采用 512 行 prefill 以保留原内存
余量，64K 的 1024 行配置继续开放。128K 的完整请求时间单独报告。

先测量共享区和单槽增长，再决定四槽能否准入。优先复用已有的 2048 行
raw QSA 索引环，完整 K/V、池化历史和绝对位置保留。索引布局必须通过
完整 raw 索引参考的同期差分。若预算超限，先减少重复存储并重新测量。

验收要求如下。

- 通过真实入口扩展容量和检查边界，保留已有 64K 与短双请求行为。
- 同期参考与候选核对完整 logits、五层特征、全部语义有效状态和后续
  验证窗口，覆盖索引环回绕、池化未完成块及 128K 边界。
- 四条 BF16 前缀真实填满并同时驻留，逐 token 控制与隔离动态控制
  核对输出及状态，再验收原生调度器驱动的四请求公开 HTTP 路径。
- 128K 位置覆盖 width 1 至 8、两种 GDN 奇偶和部分提交，检查取消、
  幸存者、旧句柄拒绝、同 ID 复用、超容量拒绝及服务恢复。
- 记录完整请求时间、首 token、纯 decode 区间、内存峰值和主机余量。
  不使用固定草稿对照，不把容量扩大解释为吞吐提升。
- 保留失败结果，更新中文优先的说明及可复核证据，运行相关 CPU 回归。

长请求仍共用串行 GPU 工作区。四个运行请求的容量与 GPU 合批分别验证。
