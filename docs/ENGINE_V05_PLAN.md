# 四请求 128K prefill 优化

2026-11-03。当前 v0.4 已完成四请求 128K，默认 512 行 prefill。
同工作量独立客户端耗时 475.44 秒。更大分块使用的 E44 专家 tile 已在
此前 32K 配对中通过，但 128K 四槽的 1024 行配置预测为 88.13 GiB。

候选保留完整 2040 行草稿特征，使用单缓冲连续布局代替双份镜像。
四请求理论减少 208896000 bytes，约 0.195 GiB。滚动时显式复制有效
后缀，复制时间计入正常执行。以此腾出空间恢复 1024 行 prefill 和已有
E44 专家 tile。target KV 保持 BF16，草稿与冻结 E17/E29 预算沿用当前配置。

对照 A 为当前 512 行、原专家、镜像特征窗口。候选 B 为 1024 行、E44 tile、
单缓冲特征窗口。所有请求均为 131008 输入加 64 输出，四个运行槽。
同一常驻模型、同一套四槽 target Graph，按 ABBA 顺序完成两组配对。
每次只保留当前 prefill 工作区。数值指纹在计时后获取。

先检查 CPU 窗口回绕、超大追加、借用视图、隔离与真实存储字节，再在 GPU
核对 1024／1025／4097 行 prefill 的完整 logits、五层特征、有效状态及
后续 width 1–8 的 Graph／部分提交。两种窗口逐步比较相同有效后缀。

完整 cohort 必须与 v0.4 封存控制逐项核对 token、有效状态和特征，
同期各运行的动态宽度、接受及预测轨迹必须一致。记录 prefill、草稿、
验证、提交、完整 wall、首 token、输出间隔、Graph／head 回退和内存。

晋升要求汇总完整 wall 至少减少 5%，两组配对均更快，最后首 token
不退化超过 2%，reserved 不超过 88 GiB，主机可用内存至少保留 8 GiB。
首请求及输出间隔的变化单独披露。通过后部署候选并由独立 HTTP 客户端
复核四长请求、排队、取消、幸存者与断连恢复。失败则恢复已验证配置。

模型继续常驻，复用现有队列，保留全部失败记录。结果范围覆盖上述合成
工作负载，decode 的纯吞吐、长 GPU 合批与 1M 容量分别验证。
