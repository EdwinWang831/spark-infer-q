# 四请求 128K 的下一轮 prefill 优化

2026-11-03。对照固定为 v0.4.1 的 1024 行 prefill、E44 专家 tile、
linear 特征窗口、BF16 target KV、完整 2040 行草稿后缀和 E17/E29
自适应 DFlash。沿用同一常驻模型，内存上限 88 GiB、主机保留 8 GiB。

先运行真实 131008-token 输入，在开头、中段和末段分别取得 CUDA
kernel trace 与独立阶段 event 诊断。使用已有 trace 区间并集统计，避免
把父段、子段和主机等待重复相加。剖析执行不进入正式性能表。
数值结果与已封存 v0.4 控制核对，剖析只操作私有 provider。

依据测得的主要成本选择一项候选。保留原专家与矩阵算术，优先消除
重复工作或优化已测算子。只有主机提交空隙足够大时才扩大 prefill
Graph 覆盖。此前被拒绝的 GDN scratch pooling 不重复试验。

候选先过完整 logits、五层特征、有效状态及后续 Graph 部分提交检查。
再以四请求各 131008 输入加 64 输出做同常驻模型、同四槽 Graph 的
ABBA 配对，比较完整 cohort、prefill、动态轨迹、TTFT、输出间隔、
内存和回退。正式样本关闭 profiler，输出和状态检查在计时外。

晋升要求完整耗时至少减少 3%，两组配对均更快，最后首 token 不
退化超过 2%，最大输出间隔不超过同期对照的 105%，所有数值检查
通过。通过后部署并独立验证 HTTP、四运行加四等待、取消与恢复。
若候选不通过，保留负结果并恢复 v0.4.1 服务。

结论限定于实测输入、64-token 输出和串行长请求 GPU 执行。
