# E53：八路256K资源核算与双请求动态验证

2026-10-26。**当前FP8布局不能在既有88GiB分配限额下支持八路256K。**
本轮将此前未计入的私有Graph、screened head、草稿缓存/Graph、请求特征窗口和
采样瞬时开销纳入预算，不提高限额、不重载权重、不清空CUDA allocator。

[事前方案](E53_LONG_CONCURRENCY_PLAN.md) · [用法](E53_LONG_CONCURRENCY_USAGE.md) · [可校验结果](../results/e53/2026-10-26-long-concurrency.json)

## 完整资源估算

在同一个常驻worker上，实际构造两份独立的262160容量FP8状态与各自16个
decode Graph，公共eager/prefill/screened head/草稿工作区共享；每请求保留
完整KV和池化QSA历史，原始索引使用E51的2048行环，草稿保留2040行特征。
容量作业只填充短prefix，没有将空分配称作两个256K请求。

| 项目 | 实测/预算 |
| --- | ---: |
| 公共常驻区 | 73.82195GiB |
| 每请求状态＋私有Graph＋特征窗口（取两槽增量较大值） | 3.60600GiB |
| 其中每请求镜像特征窗口 | 104,448,000bytes，99.61MiB |
| 采样运行瞬时峰值增量 | 120,321,024bytes，114.75MiB |
| 预算余量 | 1GiB |
| 两路估算峰值 | 82.03395GiB |
| 三路估算峰值 | 85.63995GiB；未分配或执行第三路 |
| 四路估算峰值 | 89.24595GiB；超限1.24595GiB |
| 八路估算峰值 | **103.66995GiB；超限15.66995GiB** |

预算余量取1GiB与采样运行瞬时增量加最终allocator slack的较大值，不将准备阶段
的历史峰值或已释放请求所留下的缓存反复计入每槽。Linux MemAvailable与CUDA
reserved slack来自同一统一内存，不相加。准入对新增live allocation保守扣除
host可用内存，并保留8GiB；即使放宽88GiB，当前八路外推也未满足这个host门槛。

以上八路数值仍是**预测**，不是实际八路峰值；长历史相关瞬时分配、native元数据
和系统变化需要实际运行校正。分页只能改善按需占用，八份历史各自填满后的真实
数据仍需容纳。三路资源估算通过也不意味着现有双槽Graph API支持三请求。

## 显式串行多请求适配

新增`serialized_postdraft=True`研究选项，绕过原来只允许单请求的后草稿预算限制，
但只接受已有私有Graph槽、共享串行scratch和deferred drafter，不允许把单请求
费用曲线当作GPU合批曲线。默认单请求行为及未测合批拒绝保留；不修改另一工作区K4。

每请求拥有独立target状态、FeatureWindow、接受历史、当前草稿和预算宽度。共享
drafter切换请求时先重置projection cache，再从该请求已提交后缀重建。Target仍
使用完整历史，草稿后缀上限不变。E17/E29冻结，未训练新模型或校准并发吞吐目标。

短输入为英文3073和中文4097 tokens、输出上限64；分别独立执行，再双请求执行，
取消首请求并检查另一请求，最后复用槽位。原生调度器可将prompt边界1024拆为
1023/1024/1024/1024/2，prompt分块记录单独保留；decode预算/接受轨迹逐请求比较。

## 验证与证据

两个填满的长请求已实际运行，但**严格动态轨迹门槛失败，候选不晋升**。长输入是中英合成ledger加英文教程任务，261120 tokens，
第二请求在背景位置插入等长独立标记，保留真实chat前后缀；不是自然长文质量集。

分别独立执行两个长请求，再在同一引擎提交两个请求：共处理1,044,480个长输入
tokens、2048个长输出tokens。组合中两份独立历史实际同时超过261120行，并
分别输出512 tokens。两请求的全部输出、完整已提交有效KV/pool/scale/GDN/PLE/
未完成raw尾块与2040行草稿特征指纹均匹配各自独立执行，三键检索各3/3。
这不等于FP8与BF16质量等价。

| 长请求 | 独立/组合验证轮数 | 输出及有效状态 | 与独立执行不同的decode轮数 |
| --- | ---: | --- | --- |
| A | 174/174 | 完全一致 | 概率144轮、宽度7轮、发出量2轮、接受数量2轮、观察数量3轮、起始位置1轮 |

证明它是唯一原因。不因本轮结果重新训练预测器，也不发布动态吞吐改善。
