# Kaifra v0.2：四请求与 32K 验收

2026-11-02。范围按[事先冻结的方案](ENGINE_V02_PLAN.md)，使用同一台
DGX Spark、现有完整 NVFP4 target 和 DFlash2 权重。
[中文用法](ENGINE_V02_USAGE.md) · [English usage](ENGINE_V02_USAGE.en.md) ·
[可校验的脱敏证据](../results/engine/2026-11-02-v02.json)。

公开服务默认由双请求、1536 tokens 扩展为**四个运行请求、每请求 32768
tokens（输入加输出）**，保留 BF16 target KV、动态 DFlash 和原生
Scheduler/MTPVarlen。没有修改另一工作区的未提交四路 CompactTarget。

## 实现

- E54 的私有 Graph 槽由最多两个扩到四个；共享串行 GPU 工作区。
- 保留每请求的 2040 行特征窗口与草稿投影缓存，避免切换请求时重建投影
  改变预测率与验证宽度。使用 512 行自主 prefill。
- 统一 owner 支持已有同步、带 fence 的执行器；HTTP 请求独立提交、取消
  和消费，device 串行执行如实标记 `gpu_batch=false`、`asynchronous=false`。
- CLI 增加 `--max-requests`，长路径逐槽测量状态/Graph 增量，连同草稿
  特征、投影与暂存余量一起准入；保留 88 GiB 分配上限与 8 GiB 主机余量。
- 请求体上限从 64 KiB 扩为 2 MiB；token 总容量仍单独检查。
- 原双请求短路径可用 `--capacity 1536 --max-requests 2` 保留 GPU batch。

## 正确性与容量

| 检查 | 结果 |
| --- | --- |
| 本地 CPU 回归 | 491 项：450 通过，41 项因可选环境跳过 |
| 短位置差分 | 四槽 × 两种状态奇偶 × 1–8 行，共 64 组；完整 logits、五层特征与部分提交状态精确一致 |
| 长位置差分 | 32704 位置再测两种奇偶 × 1–8 行，共 16 组；同上精确一致 |
| 同时填满的状态 | 四份独立缓存均真实处理 32704 输入 tokens，同时驻留；不是空缓存容量估算 |
| target-only 控制 | 四条输入分别逐 token 生成 64 tokens；各请求总计正好 32768 tokens |
| 动态 HTTP | 四条近 32K 中英文、代码与混合提示，混用 SSE/非流式；token、完整已提交状态、滚动特征均与 target-only 一致 |
| 隔离与动态策略 | 四路 HTTP 与各自隔离执行的 token、状态、特征、预测率、验证宽度、接受/观察轨迹一致 |
| 生命周期 | 四请求中取消一个，三个幸存者与重放一致；同 ID 复用、拒绝旧句柄、断连及恢复通过 |
| 准入 | 超出 token 容量拒绝；总流数上限为 8，可观察同一时刻四运行加四等待，第九个返回 429 |
| 打包 | wheel 安装到仓库外，CLI 可用，全部生产 Python 字节与实际 GPU 验收/常驻服务快照一致，上游许可证随包保留 |

**并发范围需要区分：**容量探针同时填满了四份 32K 前缀；正常 HTTP
cohort 中四份状态已准入，但 prefill 偏向先处理一个请求，最多一份前缀
同时达到近 32K。HTTP 的四活跃状态和独立填满的四状态各有证据，不能
把前者解释成四路长上下文 GPU batch 或公平交错 prefill。

## 内存与常驻

包含独立 eager 参考状态的验证阶段：峰值 allocated **79.67 GiB**，
峰值 reserved **80.07 GiB**，最少主机 MemAvailable **26.22 GiB**。
最终服务逐槽测得的 allocated 为 74.61、75.70、76.79、77.88 GiB；
把私有草稿缓存和 1 GiB 暂存余量计入后的准入预测为 **79.61 GiB**。
预测不是新的执行结果，实际峰值见脱敏证据。

旧双请求服务在零在途请求时退出，切换后加载 48 层一次。数值验证、
生命周期补验和最终常驻服务共享同一个模型进程及权重对象，没有第二个
并行模型进程，也没有清理 allocator 缓存或提高内存上限。

第一次新路径退出并回收验证对象后，allocated 比加载后的基线高
**64 MiB**；后续生命周期服务退出维持同一水位。保留此差值，未证明
具体来源，不能宣称首次初始化后零增量。本阶段没有重做 v0.2 独立 CLI
冷启动；[v0.1 冷启动](ENGINE_V01_REPORT.md)作为原配置历史记录保留。

## 延迟与未完成工作

独立客户端在没有数值观测回调的最终服务上，四请求共 130816 输入、
256 输出 tokens，完整 cohort 耗时 **116.02 秒**。这是包含 prefill、
排队、草稿和 decode 的单次完整请求计时，不能当作纯 decode 吞吐。
本阶段证明容量与正确性，未证明四路吞吐提速。主要待办是长请求 GPU
合批与公平 prefill；冻结 E29 成本也尚未按多路长上下文重新校准。

总流数上限是运行槽加额外名额。起步时，`pending_submissions` 包括
等待计划边界进入空闲运行槽的命令，曾短暂达到 7；四槽全部占用后可
观察到四个等待。原 30 秒准入超时保持不变，4K 提示的八请求测试曾
触发正常的超时 429；最终队列验收改用较短提示，并没有放宽服务超时。

## 保留的测试失败

首次主要数值运行已完成全部 80 组差分、四份填满状态及全部长请求精确
核对，随后因短提示生成器的重复文本不足而停止。修复测试输入后，仅补跑
缺失的生命周期项；补跑核对模型身份和所有生产源码 SHA256 一致。

首次外部客户端错误地要求不同时刻的最大 pending 恰好为 4；随后修复为
核对同一时刻的四运行加四等待。另一轮较长队列输入触发正常的 30 秒准入
超时。失败原始记录、客户端指纹和补验记录均保留，不把失败的总状态改为
通过；导出器只在完整的数值、生命周期、HTTP 和打包证据全部满足时输出
`PASS_ENGINE_V02`。

256K 统一服务、八并发、压缩 KV 精度、跨模型泛化和长期压力仍未验收。
