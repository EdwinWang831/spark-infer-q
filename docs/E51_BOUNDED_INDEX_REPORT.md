## 内存改动与来源

`bounded_index.py`创建固定完整KV容量、有限raw-index容量的State及私有Python调用命名空间。它复用外部前向函数的代码对象，不执行改写后的上游源码，不修改上游全局函数。`bounded_index_kernels.py`在每行prep和每个完整池化块进入原有TensorFold JIT体前，只转换raw-index指针；绝对RoPE位置、KV地址和池化输出地址保持原约定。原有数值算法仍归属TensorFold，MIT说明保留。

最大prepare1024、ratio4时，必须同时保留新窗口及之前未完成块的最多3行。2048行环按4行块对齐；pool完整块不会跨环边界。snapshot保存未完成raw尾部，支持回滚后重算；State复制须相同几何，固定容量扩缩和前缀迁移拒绝。target和prefill布局不匹配会在prompt启动前报错。所有选项默认关闭。

## 对首次FP8大幅增益的复核

首次FP8完整请求显示+29.75%，但只有一组、完整索引先运行。它不能直接证明raw环带来稳定29.75%加速。

追加实验先构建一份真实FP8 256K前缀：两种Graph owner使用完全相同的K/V、池化索引、eager scratch及输出头地址，独立raw索引和递归状态；在真正prefill前完成两组capture。随后交替四组AB/BA，每组各生成512 tokens；每次只恢复小状态，不复制整个KV或重新加载权重。此循环排除原生Scheduler/流式事件，因此其tok/s不作为HTTP或完整引擎速度。

修复版四组AB/BA汇总：完整索引 **38.4940 tok/s**、原始索引环 **38.4897 tok/s**，变化 **−0.0113%**；逐对变化为+0.313%、+0.238%、+0.059%、−0.658%。输出、有效状态和预算轨迹全部精确，完整K/V与池化前缀保持不变。**没有复现29.75%的稳定增益，也没有确认这个布局改动能提高decode速度。**

复测kernel归因由归档后的离线导出器生成，见证据中的`repeat`。不能将首次单组完整请求差值、seeded循环和BF16结果拼成累计提速。缓存温度/分配布局是待区分的因素；没有冷/热PLE页故障对照，不能把它们写成已证实根因。

两臂各16轮CUPTI诊断，均29888个真实kernel事件；累计核时间902.252/919.533ms，区间并集901.915/919.205ms。专家占37.21%/37.49%，量化投影26.76%/26.78%，BF16矩阵12.83%/12.81%，QSA评分选择7.16%/7.04%，attention主核1.16%/1.16%。profile按顺序单次采集，不用于正式TPS或微小差值的因果解释；CUDA annotation父级不重复计入。当前真正重核仍是专家和投影，不能把FP8首次完整请求慢全部解释为attention或Python。
