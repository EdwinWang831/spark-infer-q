# E3 后续：官方草稿对照与完整生成

**8 个请求全部生成到 EOS；72 次交错计时的输出和有效状态与 target-only 一致。固定 DFlash2 的汇总 decode 比值为 1.781×，动态为 1.789×。** 动态预算实际一直选择完整块，两者的微小差异不是动态调度收益。证据见 [公开 JSON](../results/e3/2026-10-20-followup.json)，首轮 16-token 结果保持独立。

## 参考实现与精度边界

外部使用 [DFlash 官方 PyTorch 实现](https://github.com/z-lab/dflash/blob/07ebd93db9f472af339b644bb70221ad8428328a/dflash/model.py)，SHA256 为 `f55b7fe0a4c0b3073e0f9cdce547cce29f4b8e2168c4d2818760007c43b7651e`。完整模型包含 603,065,600 个参数，原始 forward/attention/conv/selector 代码未修改，使用 Transformers 5.12.1、SDPA MATH 后端；严格加载同一批真实参数，embedding/head 从 target 共享。

- FP32 对照检查接线与数学结构：执行前设置 hidden/logits 相对 L2 均小于 0.001、候选集合重合率至少 95%。这是数值控制，不是任务质量标准。
- BF16 分别保留 SGLang 风格 fused residual/norm、卷积和激活的边界，与官方 HF 分步算术做诊断，不要求逐 bit 一致，不将数值差异解释为质量升降。
- 官方源码作为外部依赖导入，未复制入库；这不是完整 SGLang runtime 的对照，也没有提供独立整模 target oracle。

## 工作负载和测量方法

8 个事先定义的请求：加法、法国首都、Python 加法函数、翻译、JSON、量化说明，以及开启思考的算术和代码请求。使用 checkpoint 自带 chat template，前六项 `enable_thinking=False`，后两项开启思考。短答案上限 256，思考请求上限 1024，实际按 EOS 停止；达到上限必须另记截断。

- target 继续以同一 decode 算术处理 prompt，prefill/serial 数值复核保持开放。
- 容量为 1536 行，draft block 为 4 行；未进入 2048 sliding window 的淘汰区间。不能据此推断长上下文或多请求容量。
- target-only 先生成参考 token/logits；固定和动态模式逐行检查 logits、输出及最终有效状态。这些 oracle 比对放在计时外，同时暖机。
- 每任务三轮，按循环 Latin-square 轮换 serial/fixed/dynamic 的运行先后，每种模式各占一次首/中/末位。每次都复制同一起始状态、重置策略与 runtime estimator。
- 接收率初值来自两个独立校准请求，计时任务的未来输出不参与初始估计。之后只使用滞后、按深度且处理拒绝截尾的在线统计。
- 时间为同步 host wall-clock 的 decode 耗时，排除加载、prompt、首个已输出 anchor、校准与逐行 oracle/final-state 检查。不是包含 prefill 的请求总延迟，也不是跨框架服务基准。
- 动态成本曲线包含 target 验证/提交，并仅在有草稿的档位加入 drafter 实测成本；运行时更新总耗时，避免重复计入 sampler。
- 当本轮不验证草稿时，跳过 drafter；其他情况仍一次生成三个 proposal，再裁剪验证长度。target-only 无需捕获 draft 特征，其成本优势被保留。

## 限制和失败记录

首次重载后，旧 E2 包在模块搜索路径中遮蔽 E3 新模块，导致在正式实验前中止。已将旧 helper 路径调整为低优先级，并将关键模块导入前移到重量加载前检查。原始失败 JSON/log 保留在私有实验区，不当成模型或 GPU 兼容性失败。重载期间另一次预检发现 Transformers 5.12.1 的模板接口默认返回字典，已显式使用 `return_dict=False`，并在正式实验前中止、修正、重新加载；这些过程没有计入性能样本。

独立预检在 17 行合成特征上使用真实权重执行完整官方 FP32 模型：hidden 相对 L2 `4.52547e-6`，logits 相对 L2 `3.95636e-6`，候选集合及三个 proposal 相同。正式测试另核对真实 target 特征和更长位置。

公开材料只保存受控提示、生成结果、摘要和计数；权重、外部源码、依赖 wheel、二进制与原始日志不入库。

## 完整生成与交错计时结果

每个任务 serial/fixed/dynamic 各计时三次。另有固定/动态各一次逐行 oracle 检查，均满足 token、验证 logits 和最终有效状态逐 bit 一致；计时样本只在计时外检查输出/状态。所有请求自然 EOS，未触发长度上限。六项指定的字面/格式属性检查通过；两个代码结果仅保存供查看，没有执行代码测试，不把这些检查称为通用质量评测。

| 任务 | 输出 token（含 EOS） | serial 中位 ms | 固定 ms | 动态 ms | 固定比值 | 动态比值 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 17 + 25 | 3 | 82.55 | 71.50 | 72.36 | 1.154× | 1.141× |
| 法国首都 | 8 | 304.63 | 141.14 | 145.02 | 2.158× | 2.101× |
| Python 加法函数 | 18 | 722.36 | 356.82 | 360.44 | 2.024× | 2.004× |
| 早上好翻译 | 2 | 43.49 | 69.80 | 69.92 | 0.623× | 0.622× |
| JSON | 19 | 770.24 | 362.41 | 354.92 | 2.125× | 2.170× |
| 量化说明 | 54 | 2267.39 | 1692.27 | 1676.48 | 1.340× | 1.352× |
| 思考算术 | 78 | 3219.09 | 1890.73 | 1894.95 | 1.703× | 1.699× |
| 思考代码 | 113 | 4727.16 | 2231.24 | 2211.27 | 2.119× | 2.138× |

汇总为“各任务中位耗时之和”的比值，固定 1.7807×、动态 1.7887×。两者均在 7/8 任务快于 serial，最短翻译只有一个计时输出 token，草稿开销使它降至约 0.62×。完整生成长度为 2～113 token；首个已输出 anchor 不计入 decode 计时。

**72 个计时样本中，动态模式所有预算决策都为 4 行：1 anchor + 3 草稿。** 因此当前校准和成本曲线下，动态模式与固定模式选择相同，1.789× 对 1.781× 的差异不能归因于动态机制。此结论比首轮混合运行历史、仅 16 token 的探索更明确，但仍只有八种输入和三次重复，没有统计显著性或服务级性能结论。

草稿开销在独立校准中为 13.80 ms，target 1/4 行验证+提交约 42.37/52.59 ms。粗略假设每轮都接受三个草稿，当前原型的成本比约 `4*42.37/(52.59+13.80)=2.55`；这只是本次成本的估算，不是 DFlash2 的理论或优化上限。实际拒绝、提前 EOS 和额外控制开销会降低收益。

“固定草稿”在此始终指真实 DFlash2 的并行三-token proposer，不是原生 Qwen MTP。当前还不能推断它胜过同条件的原生 MTP、SGLang 服务或其他框架。

## 官方数值对照结果

| 输入 | BF16 logits 相对 L2 | FP32 logits 相对 L2 | BF16 proposal 一致 | FP32 proposal 一致 |
| --- | ---: | ---: | --- | --- |
| actual-first-row (1 行) | 4.524958% | 0.000222% | False | True |
| actual-prompt (21 行) | 1.600308% | 0.000099% | True | True |
| synthetic-position-255 (255 行) | 10.776343% | 0.000532% | False | True |

FP32 三例通过预设门槛，候选集合全部一致，三个位置的 proposal 全部一致，支持数学结构和接线。BF16 在 context 投影/归一化时已出现约 0.28% hidden 差异，后续累积；差异可改变草稿 token。不能将本轮标为“官方 BF16 数值复现完成”，也不能把 L2 百分比解释为质量下降。它可能影响接受率，但尚未单独做相同算术边界下的 A/B 归因。

## target prefill 定位对照

仍用历史四个 synthetic token IDs `[100,101,102,103]`：

| 路径 | 末行 logits 相对 decode L2 |
| --- | ---: |
| 原生 prefill（BF16 MoE slots） | 10.68136% |
| prefill 使用 F32 MoE slots / decode shared-expert 路径 | 10.69269% |

该控制没有改善差异，所以不能通过这个改动宣布修复 prefill。它同时改变了 MoE slot 存储精度与 shared-expert 路径，不是单个舍入操作的因果隔离，也不排除其他 MoE、GDN 或投影差异。正式生成测试继续使用同一 decode 算术处理 prompt；没有启用未经复核的快速 prefill。

## 资源与证据边界

- BF16 完整生成阶段 Torch allocated/reserved 峰值为 72.4119/72.4375 GiB。
- 包含额外 FP32 草稿、embedding/head 对照副本的诊断阶段峰值为 80.0135/80.8047 GiB，与实际 BF16 执行分开记账。
- 实际最长已处理位置只有 185；1536 是本轮分配容量，不能宣称已验证 1536 或更长上下文。
- cgroup 最终 events 全零；其计数范围不包含全部 CUDA 统一内存。记录结束时主机可用约 28.47 GiB，这是结束时样本，不是全过程最小值。
- 结束后停止实验容器，OOMKilled=false；未部署新服务。本地 39 项标准库测试通过，运行源码摘要逐项核对。

## 后续优先级

后续已完成[五档对照与位置重放](E3_BUDGET_AUDIT_REPORT.md)：200 次计时仍未观察到动态额外收益，但事后位置模型在混合接受任务发现约 20.3% 成本空间。该空间未由在线策略兑现，后续需评估局部接受预测和草稿前启停，不能仅因本轮始终选满就排除动态方向。

先对齐/明确草稿 BF16 算术边界，再量化草稿执行优化（例如上下文 K/V 复用）对接受率和延迟的影响。target prefill 差异另行定位，并补独立精度参考。动态预算需要能产生不同最优长度的负载和多请求成本曲线；本轮未观察到额外收益，不应优先围绕 1.79× 的微小差异继续调参。

复现需本轮 scripts/e3_followup*.py、e3_draft_parity.py、e3_prefill_control.py、e3_target.py 与项目模块，以及既有 E3 的外部源/权重/扩展。将公开 JSON 中的 `harness_sha256` 保存为实验目录 `followup-ready.json`，放置对应文件后，使用原 e3_run.sh 运行 e3_followup.py（root、checkpoint 和 repetitions=3）。官方参考源身份及私有目录安装的 wheel 摘要均在 JSON 中；它们不入库。所有关键模块与实际聊天模板返回类型在完整权重加载前检查。
