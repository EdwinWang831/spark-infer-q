# 四请求同批 prefill

2026-11-03。用户指定四请求同批，目标为每请求每步 1024 tokens，
一次聚合 4096 行。沿用四份私有 128K 状态、BF16 KV、完整草稿后缀、
E44 专家和冻结 E17/E29 动态 DFlash。模型复用当前常驻进程。

先测量工作区实际 tensor/storage 字节、使用路径和存活区间，构建本项目
的精简 prefill 工作区。数值路径沿用已验证算术，复用存储前明确最后一次
读取，异步主机复制拥有独立存活期。保留 88 GiB 分配器上限、8 GiB
主机余量与至少 1 GiB 暂存预算，实际准入检查在执行前进行。

四请求的投影、路由、专家和 hyper-connection 合批执行，GDN、QSA、
PLE 和提交使用每请求段偏移与私有状态。一次输入验证覆盖所有请求，
中途计算失败则隔离整个工作区及请求，完成设备同步后才允许释放。

DeepInfer NORMAL 调度在第一个未完成的 prompt 块后结束本轮。
采用封存头文件构建的小型 C++ 控制接口，在生成 prompt 计划期间选择
原生 PROMPT 模式，并通过 chunk_checkpoints 限制每请求块长。
finally 恢复 NORMAL，再沿用原生输出和 MTP 记账。控制接口校验原生
版本及源 SHA，模型计算由本项目执行器承接。准备好 decode 时保留其
执行机会，取消和错误路径需要单独核对。

先验证四条不同长度和不同起始位置的完整末行 logits、所有五层特征、
有效状态及 width1–8 的后续 Graph 部分提交，并覆盖尾块、请求隔离和
取消。组件测量在筛选阶段完成，正式速度判断使用完整原生引擎。

对照为封存 v0.4.1 的 1024 行串行 prefill、E44、linear 特征窗口。
候选为精简工作区及四请求同批。四请求各 131008 输入加 64 输出，
同一常驻模型、同四槽 Graph，完整 ABBA 两组成对测试。
晋升要求完整 cohort 耗时至少减少 10%，两组均更快，最后首 token
不退化超过 2%，最大相邻输出间隔不超过同期对照的 105%，数值及
内存检查全部通过。首请求和每请求 TTFT、完成时间单独披露。

通过后按显式四请求 profile 验证 HTTP、四运行加四等待、取消和恢复。
未通过则保留负结果并恢复封存服务。每个阶段使用新的唯一源快照，
所有计时包含调度、特征复制和必要同步，profiler 与数值 hash 位于
正式计时外。完整结果按实测批次大小、输入长度和输出长度报告。
