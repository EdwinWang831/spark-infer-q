## 为什么没有收益

两种post-draft策略在**全部4轮、全部9任务上，预算宽度序列完全一致**。每组每轮400个决策，4轮共1600个；两者均验证9432行、提交4548行，宽度直方图完全相同。第一轮400个相同已提交前缀位置上，动作差异为0。因而细小时间差不是由更好的验证分配带来。

原生MTPVarlen的结构检查进一步确认：在冻结E6成本曲线上，五深度二分桶的 **32种组合全部选择6行**，即anchor+5草稿。查表会改变预测概率，但在这一动作成本和概率范围内，最大宽度始终最优。EOS/cap末尾另受剩余输出空间限制。

正式计时之外追加了新合成校准前缀的成本核对，未改正式试验曲线、未在相同测试上重调再宣称独立验证：

| 校准context | 实测width1→6 verify+commit中位数ms | 32个分桶角点的原生选择 |
| --- | --- | --- |
| 384 | 43.64 / 47.08 / 50.94 / 55.08 / 58.13 / 61.26 | width5一次、width6共31次 |
| 1024 | 42.67 / 47.36 / 50.57 / 54.78 / 58.69 / 60.87 | width6共32次 |
| 1792 | 42.64 / 47.87 / 50.98 / 54.48 / 56.01 / 59.47 | width5两次、width6共30次 |

这些组合的权重并非真实请求分布，不能把1/32当作在线发生率。诊断只说明：**更新成本曲线本身仍难以让当前二分桶信号产生丰富动作。** 每种context使用固定teacher-forced草稿前缀，各宽度4次，共72次计时；不含state clone。这不是完整请求或在线策略收益。

## 新任务上的校准问题

仅取每任务第一轮margin轨迹，避免把4次相同输出当4份独立标签。仍按第一次拒绝、EOS、cap进行censor；只统计实际观察到的条件接受事件：

| --- | ---: | ---: | ---: | ---: |
| 1 | 202 | 284/396 | 71.72% | 69.00% |
| 2 | 115 | 194/283 | 68.55% | 68.22% |
| 3 | 71 | 122/192 | 63.54% | 75.44% |
| 4 | 50 | 81/120 | 67.50% | 74.57% |
| 5 | 42 | 57/81 | 70.37% | 89.10% |

深度5的原训练depth先验为93.18%，连“低margin”桶也预测86.96%。新任务上有明显过度自信；它不会因为当前边分数较低就给出接近零的接受收益。深层训练样本少、采集预算与新执行策略分布不同，都是待进一步验证的原因，不能把某一个原因当已证实的唯一解释。此表仅作新测试诊断，未回流拟合本次模型。

E13的留出Brier改善仍是当时数据上的结果；它既不保证新分布的校准，也不保证通过成本比值后能改变动作。

## 正确性、开销与常驻

- 9个新任务：6短输入，3个不同主题的合成重复背景，实际输入1024/1536/1792 token。最多生成128 token；一条任务EOS在122 token停止，其余到cap。
- **108次正式计时**全部输出token/live state一致；**27次独立oracle、3411行committed logits**与serial执行精确一致。新selector路径和margin与参考实现一致。
- 成本诊断额外18组width oracle及72次计时的logits/live state检查通过。
- 两种post-draft组都包含cache首轮构建、追加、完整draft、预算计算；margin组还包含margin GPU提取、同步和CPU传输。累计draft+budget为18.5746s / 18.6275s。该阶段差值不是独立signal kernel测量。prompt、state clone、oracle和网络均不计入decode。
- 两种post-draft组均使用同一冻结E6 verify+commit曲线。草稿已经生成时，所有动作（含width1）都加同一已付草稿成本，避免虚构“收缩到1行就省掉draft”。没有同轮Target路由输入或专家成本模型。
- 全过程同一worker PID、同一Target/DFlash权重对象，`load_count=1`。结束后保持READY；没有下载或重载权重。
- CPU测试101项：99通过、2跳过。新代码与公开数据保存在实验分支，默认执行器未改变。

原始文件保留在gitignored目录。公开结果包含实际执行源码SHA、训练表来源SHA、raw数据摘要及分析器SHA。实跑缓存helper沿用`ee7a725`版本，与当前源码只差EOF空行，详见复现说明。

## 下一步
