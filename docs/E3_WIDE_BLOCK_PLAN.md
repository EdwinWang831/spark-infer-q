# E3 八行／七草稿验证方案

在本轮 GPU 对照结果产生前固定方案。保持 checkpoint、target 权重格式和外部 SM121 内核不变，将本探针的 target buffers 和 GDN 暂存扩到八行，并把 DFlash2 的 query、卷积分组和 selector 路径参数化为四/八行。checkpoint 配置 block_size=8 不直接等同于执行验证通过。

## 正确性门槛

1. 原始 DeepInfer 预算器使用七深度概率和八档成本，在受控高/零/部分接受率下分别选 8/1/2 行。
2. 对窗口宽度 1～8 分别检查所有 keep=0～rows，共 44 例。完整 logits 和捕获特征与 serial 路径逐 bit 比较；提交后比较有效状态，再输入相同后续 token 比较 logits/特征/状态，检查拒绝后的残留不影响继续生成。
3. 参数化后的四行草稿与既有四行实现 hidden/proposal 逐 bit 相同。八行草稿对照固定、未修改的完整官方 PyTorch 模型，使用真实首行、真实 prompt、255 行 synthetic 三例。FP32 数学控制沿用事前门槛：hidden/logits 相对 L2<0.001，候选重合率≥95%；BF16 单独诊断，保留已知融合舍入边界差异，不据此宣称官方 BF16 fidelity 完成。
4. 每个非 serial 模式先核对完整输出、已提交行 logits 和最终有效状态，正式计时只在计时外比较输出与有效状态。所有测试要求自然 EOS，并核对与前一轮 serial 输出相同。

首次执行后的调用约定更正：底层 `commit` 仅接受 1..R，零保留应丢弃未提交状态。本轮 44 例因此包含 8 例丢弃和 36 例实际提交，而非调用不支持的 `commit(keep=0)`。首次失败原始日志、摘要和源码保留私有区，没有性能样本；这不是八行 GPU 兼容性结论。

## 性能对照

五组为 serial、四行草稿验证三个（fixed3）、八行草稿只验证前三个（fixed3_wide）、八行草稿验证七个（fixed7）、八行草稿加原始 DeepInfer 动态零到七个（dynamic7）。四行和八行网络的前三个 proposal 不一定相同，因此必须保留 fixed3_wide 来区分草稿布局和验证长度的收益。

八个输入复用上一轮策略测试，属于实现回归，不声称新的未见测试或广泛质量结论。每组每任务五次，按五阶循环 Latin square 轮换，共 200 次计时。用另外六个 calibration prompt 测每档 1～8 行验证/提交成本，每档每提示三次；同时记录四/八行草稿成本。八行草稿完整成本仅加到有草稿档位。动态选择零草稿时跳过 drafter，但保留 target 特征以允许以后恢复草稿；纯 serial 不捕获草稿特征。

原动态调用相同固定 DeepInfer 二进制。接受率来自六个独立提示的新七深度观测，Beta(1,1) 计数，拒绝后的深度不计失败；每次测试从相同先验重置，使用强度四的 lagged online 更新和原始运行成本估计器。稀少的深度 6/7 观测和缺少学习置信度头作为限制保留，不把新范围退化成“三头概率外推七头”。本轮不移植旧的三头局部预测器。

首次调用约定修正后的权重重载期间、任何八行 GPU 结果产生前，补充一个必要对照：仅用六个 calibration prompt 和启动成本选定全局固定宽度，测试前冻结。主实验之后独立比较该固定宽度、fixed7、dynamic7，八任务每组三次，按三阶循环 Latin square 轮换，另计 72 次，附加 24 次 logits/状态检查。该对照用于判断收益来自在线调整还是仅选到较好的静态长度，不依据测试结果选择固定档位；不声称其必为所有固定档位的真实最优。

计时包含草稿、target 验证、状态提交、同步与控制开销，排除加载、prompt、首个已输出 pending token、校准、状态初始化和 oracle 检查。为隔离长度因素，五组均不使用上一轮 norm/RoPE 缓存或 EOS 验证截断，也不启用随机采样。报告实际预算长度分布、每任务中位数/范围、输出 token/s、接受步长和成本。若动态仍选满或更慢，照实保留结果。

四行和八行草稿共享同一批 BF16 参数，FP32 诊断副本释放后重置峰值，单独记录诊断/正式阶段资源。原始权重、官方源、二进制和私有日志不入库；公开实验代码、摘要和受控输出。长上下文、完整引擎、多请求、独立 target 质量、官方 BF16 差异及 target prefill 问题不因本轮关闭。
